### 1.2 后续固定开发准则（长期有效）

- 严格按需求文档与设计文档开发，采用“一个功能点一个功能点落地”的分段式推进方式。
- 严格遵守前后端分离模式：前端仅负责页面、状态、交互与 API 调用；后端仅负责接口、鉴权、业务与数据访问。
- 设计核心固定为“社区志愿服务管理”，不引入与主业务无关的功能方向。
- 开发过程中优先使用高质量、最小必要 skill；允许按需安装，但禁止一次性堆积大量 skill。
- 系统 UI 需保持统一设计语言，并在管理员端、志愿者端、门户端之间保持有区分但不割裂的体验。
- 每轮开发都要同步更新相关文档，并持续整理目录结构，避免仓库臃肿。
- 技术选择优先稳定、兼容现有框架、可维护的方案，不为追新而引入高风险依赖。
- 数据库职责严格分层：`init-database.sql` 只负责建库建账号，`db/migration/V*.sql` 只负责结构/对齐迁移，`db/migration/R*.sql` 只负责可重复参考数据，禁止重新混用 `spring.sql.init`。
- 所有实现必须以现有项目框架为基础，以正式设计文档为目标，不做脱离基线的推倒重来。
- 持续执行代码优化：收敛重复代码、删除废代码/无效代码、移除不必要结构、缩减臃肿模块。
- 开发过程中要及时汇报当前进度、下一步方向与阻塞点；当用户要求阶段确认时，进入下一步前必须得到用户确认。

### 1.3 skill 使用约束

- 开发过程中必须优先使用 skill，必须积极使用 skill。
- 在排查问题、浏览器联调、页面验收、文档处理、测试验证、总结归档等场景，默认先判断是否已有合适 skill；只要存在匹配 skill，就不得跳过或被动使用。
- 当前项目优先采用的最小 skill 组合：
  - `playwright`：浏览器链路验证、冒烟流程、页面交互排查
  - `playwright-interactive`：仅在需要持续交互式 UI 排查时启用
  - `doc` / `pdf`：仅在文档或版式任务明确需要时启用
- 如后续出现明确收益，再按需安装额外 skill；单轮优先控制在“少量高质量 skill”范围内。
