## 1. 本轮结论

本阶段不适合继续零散补页面，必须先把角色边界、数据模型、信息架构和关键逻辑链一起收口。

结合当前仓库实际实现、你本轮提出的新增要求、以及已经完成的第一批边界修正，当前结论如下：

- 当前系统已经具备管理员端、登录注册端、门户端三类基础能力，但仍然处于“结构有了、闭环不足”的阶段。
- 你要求的重点不是单个页面好不好看，而是“管理员后台完整可运营、主页面真正可交互、用户行为链路能闭环、空内容不能发布、角色边界不能混乱”。
- 当前代码已经完成一小部分预备收口，后续不需要推倒重来，但必须在此基础上继续做一次中等强度的结构整理。
- 为了加快开发进度，本轮建议保留现有 `/portal/*` 作为“主页面路由组”，而不是强行改造成 `/`。用户体验上仍然是主页面，技术上可以减少不必要返工。
- 本轮规划完成后，建议按 3 次实施迭代推进；每次迭代都必须可单独验收，不允许把大量“能看不能用”的半成品堆到最后一起补。

## 3. skill 策略与结果

本轮严格遵守“少量、高价值、后续直接能用”的原则，不继续堆积 skill。

### 3.1 已采用的最小 skill 组合

- 当前会话已可直接配合使用的高价值 skill：
  - `playwright`
  - `playwright-interactive`
  - `doc`
  - `pdf`
- 已下载到本地 skill 目录、供后续阶段使用的补充 skill：
  - `security-threat-model`
  - `spreadsheet`

### 3.2 本轮不再继续安装更多 skill 的原因

- 当前阶段主要是业务规划与模块补全，不需要一次性引入更多工具。
- `security-threat-model` 已足够支持后续权限边界、审核链、上传链、认证链的风险复核。
- `spreadsheet` 已足够支持后续统计项梳理、字段映射、验收矩阵整理。
- 按 `skill-installer` 规则，新安装的 skill 更适合在后续新会话中自动拾取；因此当前继续安装更多 skill 的收益很低。

结论：

- skill 数量保持当前规模即可，本轮不再新增 skill。

## 7. 建议的结构优化方案

## 7.1 总体边界方案

为减少返工、加快开发，本轮建议采用以下最终边界：

- 登录界面：`/login`
- 注册界面：`/register`
- 主页面路由组：`/portal/*`
- 管理员后台：`/admin/*`

配套规则：

- 管理员登录成功后一律进入 `/admin/*`
- 志愿者登录成功后一律进入 `/portal/*`
- 管理员携带登录态访问 `/portal/*` 时直接重定向后台
- 志愿者所有自助能力统一并入主页面头像下拉菜单及其关联页面
- `/volunteer/*` 不再保留为主要产品入口，只作为过渡期兼容或后续收敛目标

## 7.2 建议新增的必要能力

- 活动详情页
- 动态详情页
- 公告详情页
- 帖子详情页
- 热点信息展示位
- 用户头像下拉菜单
- 志愿者认证表与认证链路
- 积分商品表
- 积分变更记录表
- 完整订单字段与订单状态链
- 浏览量更新接口
- 富文本编辑统一模板

## 7.3 建议删减或收拢的能力

- 删减“独立志愿者工作台作为主入口”的产品心智
- 删减管理员端“返回门户”入口
- 收拢原用户中心相关能力，统一放入主页面头像下拉菜单
- 收拢管理员菜单，弱化与本阶段主线无关的独立设置入口

## 7.4 统一 UI 与表单规则

本阶段所有新增或重做页面统一遵守以下规则：

- 新增/编辑界面使用标准弹窗或独立页面，不使用右侧抽屉
- 删除操作统一使用红色垃圾桶图标
- 编辑、审核、查看、恢复等操作尽量改用图标按钮加 tooltip
- 所有表单必须做前端规则校验和后端兜底校验
- 标题、正文、分类、时间、数量、积分、库存等关键字段禁止空白值、非法值或逻辑冲突值

## 8. 本阶段必须跑通的四条核心逻辑链

## 8.1 志愿活动链

管理员创建活动 -> 用户查看活动详情 -> 用户填写报名理由 -> 管理员审核报名 -> 用户签到/签退 -> 系统发放积分 -> 用户查看报名与打卡记录 -> 管理端统计回显

## 8.2 内容发布与审核链

管理员发布动态/公告 -> 用户在主页面查看详情并互动

用户发布论坛帖子 -> 管理员审核帖子 -> 审核通过后前台展示 -> 用户查看详情、浏览量更新、评论互动

## 8.3 积分商城链

活动完成获得积分 -> 主页面查看商品 -> 提交兑换 -> 校验积分与库存 -> 生成兑换订单 -> 后台订单管理 -> 用户查看订单状态

## 8.4 志愿者认证链

用户提交真实姓名、身份证号、身份证图片 -> 管理员审核 -> 通过或拒绝并写回理由 -> 用户在主页面查看认证状态

## 9. 冻结状态机

为避免后续 CRUD 和审核逻辑写散，本阶段先冻结六类状态机。后续开发默认遵守以下流转规则，非明确批准不得扩张状态或绕过状态校验。

### 9.1 活动状态

| 状态 | 含义 | 允许流转到 | 不允许的流转 |
| --- | --- | --- | --- |
| `DRAFT` | 草稿，未发布 | `PUBLISHED`、`CANCELLED` | 不能直接到 `ONGOING`、`FINISHED` |
| `PUBLISHED` | 已发布，报名中 | `ONGOING`、`CANCELLED` | 不能直接回 `DRAFT` |
| `ONGOING` | 进行中 | `FINISHED`、`CANCELLED` | 不能回 `PUBLISHED`、`DRAFT` |
| `FINISHED` | 已结束 | 无 | 不能回到任何前置状态 |
| `CANCELLED` | 已取消 | 无 | 不能重新发布 |

补充规则：

- 开始时间必须早于结束时间。
- `PUBLISHED` 状态的活动必须有完整分类、标题、图片、简介、详情、时间、积分、人数限制。
- `ONGOING` 和 `FINISHED` 状态原则上由系统时间或管理员明确动作推进，不允许前台用户触发。

### 9.2 报名申请状态

| 状态 | 含义 | 允许流转到 | 不允许的流转 |
| --- | --- | --- | --- |
| `PENDING` | 待审核 | `APPROVED`、`REJECTED`、`CANCELLED` | 不能重复提交为 `PENDING` |
| `APPROVED` | 已通过 | `CHECKED_IN`、`CANCELLED` | 不能改成 `REJECTED` |
| `REJECTED` | 已拒绝 | 无 | 不能重新改为 `APPROVED` |
| `CHECKED_IN` | 已完成签到，待签退或已进入服务过程 | `COMPLETED` | 不能回 `APPROVED` |
| `COMPLETED` | 已完成服务闭环 | 无 | 不能退回任何前置状态 |
| `CANCELLED` | 用户取消或系统失效 | 无 | 不能重新激活 |

补充规则：

- `REJECTED` 必须填写拒绝理由。
- 占用活动名额的只统计 `APPROVED`、`CHECKED_IN`，不统计 `REJECTED`、`CANCELLED`。
- 一名志愿者对同一活动只允许存在一条有效申请。

### 9.3 打卡状态

| 状态 | 含义 | 允许流转到 | 不允许的流转 |
| --- | --- | --- | --- |
| `NOT_STARTED` | 尚未签到 | `SIGNED_IN` | 不能直接签退 |
| `SIGNED_IN` | 已签到 | `SIGNED_OUT` | 不能重复签到 |
| `SIGNED_OUT` | 已签退 | 无 | 不能再次签到或签退 |
| `EXCEPTION` | 异常状态，需人工处理 | `SIGNED_OUT`、`INVALID` | 不能直接视为正常完成 |
| `INVALID` | 无效记录 | 无 | 不能恢复为正常记录 |

补充规则：

- 只有报名状态为 `APPROVED` 的志愿者才能签到。
- 签退后才允许进入积分发放判定。
- 异常状态需要后台介入处理，不允许前台自行更改。

### 9.4 帖子审核状态

| 状态 | 含义 | 允许流转到 | 不允许的流转 |
| --- | --- | --- | --- |
| `PENDING` | 待审核 | `APPROVED`、`REJECTED` | 不能重复提交为 `PENDING` |
| `APPROVED` | 审核通过 | `ARCHIVED` | 不能直接改为 `REJECTED` |
| `REJECTED` | 审核拒绝 | 无 | 不能再改成 `APPROVED` |
| `ARCHIVED` | 已归档下线 | 无 | 不能重新恢复到审核流程 |

补充规则：

- `REJECTED` 必须填写审核意见。
- 前台只展示 `APPROVED` 状态帖子。

### 9.5 志愿者认证审核状态

| 状态 | 含义 | 允许流转到 | 不允许的流转 |
| --- | --- | --- | --- |
| `UNSUBMITTED` | 未提交认证 | `PENDING` | 不能直接通过 |
| `PENDING` | 待审核 | `APPROVED`、`REJECTED` | 不能重复提交并产生并发审批 |
| `APPROVED` | 审核通过 | 无 | 不能回退 |
| `REJECTED` | 审核拒绝 | `PENDING` | 不能直接改为 `APPROVED`，必须重新提交 |

补充规则：

- `REJECTED` 必须记录拒绝理由。
- 用户重新提交时应生成新的待审核版本或覆盖待审核材料，但必须保留最近一次审核结论。

### 9.6 兑换订单状态

| 状态 | 含义 | 允许流转到 | 不允许的流转 |
| --- | --- | --- | --- |
| `CREATED` | 订单已创建，待后台处理 | `SHIPPED`、`CANCELLED` | 不能直接签收 |
| `SHIPPED` | 已发货或待签收 | `RECEIVED` | 不能退回 `CREATED` |
| `RECEIVED` | 已签收 | 无 | 不能再变更为其他状态 |
| `CANCELLED` | 已取消 | 无 | 不能重新激活 |

补充规则：

- 订单创建成功时积分和库存必须已经扣减成功。
- `CANCELLED` 仅允许在后台未发货前执行；是否返还积分作为后续可扩展策略，本阶段默认不自动返还，避免复杂分支。

## 11. 统一上传规则

为避免后续图片链路混乱，本阶段统一四类上传规则。

- 后端校验 MIME 类型和扩展名，不能只信任前端。
- 文件名统一重命名，禁止保留用户原始文件名直接落盘。
- 身份证图片默认不进入公开资源目录，不允许匿名访问。

## 13. 幂等与并发保护

积分和库存是本阶段最容易出生产事故的地方，必须在计划阶段先冻结规则。

### 13.1 积分发放幂等

- 活动积分发放必须以“活动申请完成 + 打卡闭环 + 未发放过”为前提。
- 建议通过 `points_change_log` 上的业务唯一键控制重复发放。
- 同一活动、同一用户、同一积分来源只能成功入账一次。

### 13.2 商城兑换幂等

- 兑换动作必须在单事务中完成：
  - 校验积分
  - 校验库存
  - 扣减积分
  - 扣减库存
  - 创建订单
  - 写积分流水
- 对同一次兑换请求建议使用请求幂等键或服务端唯一业务单号避免重复下单。
- 库存扣减必须防止并发穿透，不允许扣成负数。

### 13.3 并发控制建议

- 商品库存更新采用乐观锁字段或条件更新。
- 积分扣减采用条件更新，确保余额充足才允许扣减。
- 订单创建失败时必须整体回滚，不能出现“扣了积分但没单”或“有单但没扣库存”的中间态。

## 14. 富文本安全策略

动态、公告、活动详情等内容如果支持富文本，本阶段必须同步引入安全清洗。

建议冻结以下规则：

- 仅允许白名单标签与安全属性。
- 去除脚本标签、内联事件、危险外链协议。
- 图片、链接等资源统一走安全属性处理。
- 富文本保存前后端都做处理：
  - 前端尽量做基础过滤，提升体验
  - 后端做最终白名单清洗，作为安全兜底

结论：

- 富文本不是“能编辑就行”，必须带安全清洗一起落地。

## 15. `/volunteer/*` 过渡方案

为避免主页面并入用户能力时出现导航和回跳混乱，本阶段冻结旧路由过渡策略。

### 15.1 过渡原则

- `/volunteer/*` 不再作为主要产品入口。
- 过渡期保留旧路由，但统一做“兼容跳转”。
- 新入口全部指向 `/portal/*` 对应功能页面或弹层。

### 15.2 过渡执行方式

| 旧路由类型 | 处理方式 |
| --- | --- |
| 列表型自助页 | 重定向到头像下拉菜单对应页面 |
| 详情型页面 | 优先重定向到主页面对应详情页 |
| 已无业务价值的旧页 | 直接下线或返回主页面默认页 |

### 15.3 收口目标

- 新开发不再继续往 `/volunteer/*` 增加功能。
- 本阶段结束后，用户视角只保留主页面体系，不再需要理解“工作台”和“主页面”两套心智。

## 16. 验收矩阵建议

为避免每轮开发后遗漏链路，本阶段建议按统一验收矩阵推进。

| 模块 | 关键动作 | 成功条件 | 失败条件 | 验证方式 |
| --- | --- | --- | --- | --- |
| 登录分流 | 志愿者登录 | 进入 `/portal/*` | 进入后台或异常跳转 | 路由守卫测试 + 冒烟 |
| 登录分流 | 管理员登录 | 进入 `/admin/*` | 进入主页面 | 路由守卫测试 + 冒烟 |
| 活动管理 | 新增活动 | 必填项齐全可保存 | 缺字段、时间非法、人数非法仍保存成功 | 前后端测试 |
| 报名申请 | 提交报名 | 成功生成待审核记录 | 重复申请或空理由仍成功 | 后端服务测试 + 冒烟 |
| 报名审核 | 管理员审核 | 状态按规则流转 | 非法回退或拒绝无理由 | 后端测试 |
| 打卡 | 签到签退 | 状态按顺序完成 | 未审核通过即可签到，或重复签到 | 冒烟 + 后端测试 |
| 发帖审核 | 用户发帖并管理员审核 | 通过后前台展示 | 审核未通过也展示，或空帖可提交 | 前后端测试 |
| 信息动态 | 发布动态 | 标题、来源、详情完整保存 | 空标题、空来源、空正文仍保存 | 前后端测试 |
| 积分商城 | 兑换商品 | 扣积分、扣库存、生成订单一次成功 | 重复扣分、库存负数、订单中间态 | 服务测试 + 事务测试 |
| 志愿者认证 | 提交与审核 | 状态可追踪，拒绝理由可回显 | 无身份证图片仍提交成功 | 前后端测试 |
| 用户自助 | 头像下拉访问功能 | 菜单完整且直达目标页 | 仍依赖旧工作台主入口 | 冒烟 + 人工验收 |
| 图片上传 | 上传图片 | 符合类型大小限制并正确回显 | 非法文件可上传或路径混乱 | 上传接口测试 |

## 17. 冻结删除语义

不是所有“删除”都应该做成物理删除。本阶段冻结以下删除语义，后续实现必须按数据完整性优先处理。

### 17.1 优先归档或停用，不做物理删除

| 模块 | 删除语义 | 原因 |
| --- | --- | --- |
| 志愿活动 | 归档 / 停用 | 避免打断报名、打卡、积分、统计链 |
| 论坛帖子 | 归档 / 下线 | 避免打断评论、浏览量、审核记录 |
| 系统公告 | 归档 / 下线 | 避免历史内容与统计口径断裂 |
| 商城商品 | 停用 / 下架 | 避免打断历史订单快照 |
| 用户 | 停用 / 禁用 | 避免打断报名、帖子、订单、积分流水关联 |

### 17.2 允许物理删除

| 模块 | 删除语义 | 约束 |
| --- | --- | --- |
| 评论信息 | 物理删除 | 删除后不应影响主业务统计主线 |
| 轮播图信息 | 物理删除 | 仅影响展示，不应残留无效资源记录 |
| 无效测试数据 | 物理删除 | 仅限显式测试标记数据 |

### 17.3 特殊对象处理原则

| 模块 | 删除语义 | 约束 |
| --- | --- | --- |
| 活动分类 | 仅在无关联活动时允许物理删除 | 有关联时拒绝删除 |
| 帖子分类 | 仅在无关联帖子时允许物理删除 | 有关联时拒绝删除 |
| 兑换订单 | 不允许物理删除 | 保留完整履约历史 |
| 积分流水 | 不允许物理删除 | 保留积分审计链 |
| 认证记录 | 不允许物理删除 | 保留审核历史 |

结论：

- 后台页面上的“删除”按钮，后续必须按模块真实语义落地为“归档 / 停用 / 物理删除”，不能全部做成同一种实现。

## 18. 管理员操作审计日志

为便于后续追溯“谁在什么时间改了什么”，本阶段建议把管理员审计日志作为基础能力纳入计划。

### 18.1 最低记录范围

- 审核报名申请
- 审核论坛帖子
- 审核志愿者认证
- 删除或归档内容
- 修改订单状态
- 后续若增加人工积分调整，也必须进入审计日志

### 18.2 最低字段建议

| 字段 | 说明 |
| --- | --- |
| `operator_id` | 操作人 ID |
| `operator_name` | 操作人账号或姓名 |
| `action_type` | 动作类型，例如审核、归档、删除、发货、签收 |
| `target_type` | 目标对象类型，例如活动、帖子、订单、认证 |
| `target_id` | 目标对象 ID |
| `target_label` | 目标对象可读标识，例如标题、订单号 |
| `result` | 成功 / 失败 |
| `reason` | 审核意见或操作理由 |
| `created_at` | 操作时间 |

### 18.3 设计原则

- 审计日志默认只增不改，不允许人工回写。
- 审计日志优先用于后台排查和合规追踪，不作为用户前台展示数据。
- 审核拒绝、归档、订单状态变更等关键动作应与业务操作同事务提交，避免出现“业务成功但没日志”。

| 志愿活动数量 | 统计未物理删除且未归档的活动，默认不含已取消、已归档 |
| 各类型志愿活动分布图 | 统计当前可运营活动的分类分布，默认不含已归档活动 |
| 社区帖子数量 | 默认统计审核通过且未归档帖子 |
| 每日活动报名趋势图 | 以报名申请创建时间为统计口径，不以审核通过时间计算 |
| 志愿者数量 | 默认统计正常状态志愿者账号，可包含未认证用户，但需在说明中写清 |
| 不同类型论坛帖子数量统计图 | 默认统计审核通过帖子，按帖子分类汇总 |
| 兑换订单数量 | 默认统计已创建且未取消订单；如需要显示总订单数，应单独标注 |

补充规则：

- 图表口径必须与后台列表页提供的默认筛选范围保持一致或明确标注差异。
- 待审核数量类卡片应以当前实时状态为准，不与历史归档数据混算。

## 24. 历史快照策略

本阶段补全的多个模块都涉及“源数据后续会变化，但历史记录必须保持可读”的问题，因此建议冻结业务快照策略，避免后期详情页和历史页出现错乱。

### 24.1 必须保存快照的对象

| 业务对象 | 必须快照的字段 | 原因 |
| --- | --- | --- |
| 兑换订单 | 商品名称、商品图片、单件积分、兑换数量、收货人、电话、地址 | 商品后续可能下架、改名、改图、改积分规则 |
| 报名申请 | 活动名称、活动开始时间、活动结束时间 | 活动后续可能被归档、改名、改时间 |
| 收藏记录 | 活动标题、活动时间、活动封面 | 活动后续可能被归档或修改展示信息 |
| 审计日志 | 目标对象名称或编号 | 原对象后续可能变更，日志仍需可读 |

### 24.2 快照设计原则

- 历史快照优先用于展示和审计，不替代主表做业务计算。
- 快照生成时机应与主业务动作同事务提交。
- 若主对象后续被归档、下架、改名，历史页仍优先展示快照字段，避免出现“历史记录名称丢失”。

## 25. 状态变更责任边界

除了冻结状态机本身，本阶段还应冻结“谁能推动状态变化”，否则后续很容易出现多入口同时改状态的混乱。

### 25.1 用户触发

| 角色 | 可触发动作 |
| --- | --- |
| 游客 | 不触发业务状态变更 |
| 志愿者 | 提交报名、取消报名、签到、签退、提交认证、发帖、评论、收藏、兑换 |

### 25.2 管理员触发

| 角色 | 可触发动作 |
| --- | --- |
| 管理员 | 发布活动、归档活动、审核报名、审核帖子、审核认证、下架商品、修改订单状态、归档或删除后台可管理内容 |

### 25.3 系统触发

| 触发主体 | 可触发动作 |
| --- | --- |
| 系统任务或服务层规则 | 活动由进行中转为已结束、统计汇总、满足条件后积分发放、旧路由兼容跳转 |

### 25.4 责任边界原则

- 同一个状态变化必须有明确唯一的主责任入口。
- 前台不能直接改后台审核状态。
- 后台不能绕过业务约束直接伪造用户完成态。
- 系统自动推进的状态必须可追踪、可审计。

## 26. 旧数据回填策略

本阶段会新增多个字段和新表，如果不先定义历史数据回填策略，迁移后容易出现页面空白、排序异常或旧详情页报错。

### 26.1 默认回填方案

| 数据对象 | 回填策略 |
| --- | --- |
| 老活动 `point_reward` | 默认回填 `0` |
| 老报名记录 `apply_reason` | 默认回填“历史数据未记录报名理由” |
| 老动态 `source` | 默认回填“平台发布”或“历史数据” |
| 老帖子 `cover_image` | 使用统一默认封面 |
| 老帖子 `summary` | 由正文截断生成，若正文为空则回填默认说明 |
| 老用户 `points` | 默认回填 `0` |
| 老订单缺收货快照 | 标记为“历史订单”，尽量保留已知字段 |
| 老认证数据缺失 | 默认状态为 `UNSUBMITTED` |
| 老收藏缺活动快照 | 使用惰性补齐或迁移脚本一次性补齐 |

### 26.2 回填原则

- 默认值要保证页面可展示、接口可排序、逻辑可兜底。
- 回填后的历史数据必须与当前新增校验规则兼容，避免旧数据导致新页面报错。
- 对无法完整恢复的历史字段，优先标记为“历史数据”而不是伪造精确值。

## 27. 分阶段优化建议

| 阶段 | 范围 | 目标 | 验收重点 |
| --- | --- | --- | --- |
| P0 当前基线 | 登录分流、管理员主页面隔离、部分空内容校验、活动弹窗收口 | 建立开发起点 | 已完成，不回滚 |
| 迭代一 | 结构边界、数据模型、统一校验、剩余抽屉改标准模式 | 为后续模块补全打地基 | 角色边界硬隔离、数据迁移可用、表单校验到位 |
| 迭代二 | 管理员后台首页、信息管理、用户管理 | 后台完整可运营 | 后台模块齐全、CRUD 与批量删除可用、统计可看 |
| 迭代三 | 主页面六大模块、详情页、头像下拉自助、积分商城、订单闭环 | 前台真正可交互 | 详情可进、行为可做、数据可回查、商城可用 |

## 28. 需要确认的默认决策

为避免后续反复返工，建议将以下内容作为默认决策：

- 不强改主页面物理路由为 `/`，保留 `/portal/*` 作为主页面主路由组。
- 志愿者独立工作台不再作为主入口，逐步并入主页面头像下拉和详情页体系。
- 志愿者认证采用独立认证表，而不是继续把所有字段堆到 `sys_user`。
- 积分规则默认采用“活动完成后发放，兑换商品时扣减”。
- 本阶段允许中等规模重构，但只围绕“社区志愿服务管理”主线，不额外扩展无关功能。

## 29. 本轮报告结论

当前项目并不是“缺几个页面”，而是需要一次有边界的结构收口。

从开发效率、返工成本和你提出的目标一致性来看，最优方案不是继续零散补单页，而是：

- 先固定边界
- 再补后台
- 最后补主页面闭环
