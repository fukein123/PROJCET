## 1. 计划总览

本计划面向“系统功能补全阶段”，目标不是继续零散补页面，而是在当前代码基线之上，完成一次有边界的结构补全。

本阶段最终要达到的结果是：

- 管理员后台与主页面彻底分离
- 管理员登录后只进入后台，志愿者登录后只进入主页面
- 管理后台完成“系统首页 / 信息管理 / 用户管理”三大模块补全
- 主页面完成“首页 / 志愿活动 / 信息动态 / 社区论坛 / 积分商城 / 系统公告”六大模块闭环
- 志愿者原本分散在独立工作台的能力并入主页面头像下拉菜单和对应详情页
- 关键新增与编辑链路都具备前后端双重校验，禁止空内容发布
- 至少完成 3 次实施迭代，并在每次迭代结束后可独立验收

## 5. 本阶段实施总范围

## 5.1 后台范围

管理员后台最终重组为三组菜单：

- 系统首页
- 信息管理
- 用户管理

其中：

- 系统首页负责统计卡片、图表、待审核项提醒。
- 信息管理负责所有业务信息的增删改查、审核、批量删除。
- 用户管理负责志愿者信息、管理员信息、认证审核。

## 5.2 主页面范围

主页面最终包含：

- 首页
- 志愿活动
- 信息动态
- 社区论坛
- 积分商城
- 系统公告

并统一补齐：

- 详情页承接
- 评论互动
- 浏览量更新
- 收藏、报名、兑换、发帖等行为闭环
- 页面底部“社区志愿服务声明 + logo 样式”
- 用户头像下拉菜单

## 5.3 用户自助范围

原本分散在用户中心或志愿者工作台的能力，统一收拢到主页面头像下拉菜单：

- 报名申请
- 打卡记录
- 我的评论
- 兑换订单
- 我的帖子
- 我的收藏
- 个人中心
- 认证信息
- 修改密码
- 退出登录

## 5.4 本阶段不主动扩展的范围

为了保证范围可控，本阶段默认不做以下扩张：

- 不新增支付能力
- 不新增消息中心或站内私信
- 不新增地图导航或地理围栏签到
- 不新增复杂导出导入体系
- 不新增与志愿服务主线无关的社区玩法

## 6.2 接口与校验补齐原则

- 所有创建/更新接口统一采用 DTO，不再直接以实体类作为请求入参。
- 后端统一加 `@Valid`、非空、长度、枚举、时间范围、状态迁移约束。
- 前端所有表单统一做必填校验、空白裁剪、时间合法性校验。
- 所有发布、创建、提交、兑换、审核动作都必须有后端兜底约束，不能只依赖前端校验。

## 6.3 冻结状态机实施要求

进入开发前，以下状态机视为冻结规则，后续实现按此落地。

### 活动状态

- `DRAFT -> PUBLISHED -> ONGOING -> FINISHED`
- `DRAFT / PUBLISHED / ONGOING -> CANCELLED`
- `FINISHED`、`CANCELLED` 为终态

### 报名申请状态

- `PENDING -> APPROVED / REJECTED / CANCELLED`
- `APPROVED -> CHECKED_IN / CANCELLED`
- `CHECKED_IN -> COMPLETED`
- `REJECTED`、`COMPLETED`、`CANCELLED` 为终态

### 打卡状态

- `NOT_STARTED -> SIGNED_IN -> SIGNED_OUT`
- 异常处理路径：`EXCEPTION -> SIGNED_OUT / INVALID`

### 帖子审核状态

- `PENDING -> APPROVED / REJECTED`
- `APPROVED -> ARCHIVED`
- `REJECTED`、`ARCHIVED` 为终态

### 认证审核状态

- `UNSUBMITTED -> PENDING`
- `PENDING -> APPROVED / REJECTED`
- `REJECTED -> PENDING`
- `APPROVED` 为终态

### 兑换订单状态

- `CREATED -> SHIPPED -> RECEIVED`
- `CREATED -> CANCELLED`
- `RECEIVED`、`CANCELLED` 为终态

### 状态机硬约束

- 拒绝类状态必须记录理由。
- 所有状态迁移必须在后端服务层校验，前端只负责展示和禁用非法按钮。
- 非法状态迁移必须直接拒绝，不能做静默兼容。

## 6.6 细粒度校验实施要求

除“非空校验”外，本阶段还必须补齐以下约束：

- 开始时间必须早于结束时间。
- 最大参加人数必须大于 `0`。
- 活动积分不得为负。
- 商品积分消耗不得为负。
- 商品库存不得为负。
- 数量类字段必须大于 `0`。
- 分类必须合法且已存在。
- 必传图片场景必须上传成功后才允许提交。
- 发帖、公告、动态、活动详情富文本都必须经过去空白与安全清洗。

## 6.7 幂等与并发保护实施要求

- 活动积分发放必须通过唯一业务键防重复入账。
- 商城兑换必须在单事务中完成“校验积分、校验库存、扣积分、扣库存、创建订单、写流水”。
- 库存和积分更新要采用防并发穿透策略，不允许扣成负数。
- 订单创建失败必须整体回滚。

## 6.8 富文本安全实施要求

- 富文本保存前必须做白名单清洗。
- 禁止脚本标签、危险协议链接、内联事件。
- 最终安全兜底必须放在后端。

## 6.9 `/volunteer/*` 过渡方案

- 不再往 `/volunteer/*` 新增任何新功能。
- 过渡期保留旧路由，但统一重定向到 `/portal/*` 对应页面。
- 本阶段结束时，主入口只保留主页面体系和管理员后台体系。

## 6.10 删除语义实施要求

- 志愿活动、论坛帖子、系统公告、商城商品、用户默认采用“归档 / 停用 / 下架”，不做物理删除。
- 评论信息、轮播图信息、显式测试标记的无效数据允许物理删除。
- 活动分类、帖子分类仅在无关联数据时允许物理删除。
- 兑换订单、积分流水、认证记录不允许物理删除。

## 6.11 管理员操作审计日志要求

至少覆盖以下后台动作：

- 审核报名申请
- 审核论坛帖子
- 审核志愿者认证
- 删除或归档内容
- 修改订单状态
- 后续若增加人工积分调整，也必须进入审计日志

最低字段：

- 操作人
- 操作时间
- 目标对象类型
- 目标对象标识
- 动作类型
- 操作结果
- 原因或备注

## 6.13 敏感信息脱敏要求

- 列表页默认脱敏展示电话、邮箱、身份证号、收货地址。
- 身份证图片不在列表中直接展示原图。
- 详情页仅限具备权限的管理员查看完整敏感信息。
- 身份证图片必须通过受控资源访问，不允许匿名直链。
- 在未实现导出功能前，不允许暴露原始文件物理路径。

| --- | --- |

## 6.15 反刷与频率限制要求

- 评论：同一用户最短间隔 30 秒，短时间重复内容拒绝。
- 发帖：同一用户最短间隔 60 秒。
- 报名：同一用户同一活动仅允许一个有效申请。
- 兑换：同一用户同一商品短时间重复请求需做幂等拦截。

## 6.16 统计口径冻结要求

| 统计项 | 口径 |
| --- | --- |
| 志愿活动数量 | 默认不含已取消、已归档活动 |
| 活动分类分布图 | 默认统计当前可运营活动 |
| 社区帖子数量 | 默认统计审核通过且未归档帖子 |
| 报名趋势图 | 按申请创建时间统计 |

| 论坛帖子分类统计图 | 默认统计审核通过帖子 |
| 兑换订单数量 | 默认不含已取消订单 |

## 6.17 历史快照策略

- 兑换订单必须保存商品名称、商品图片、单件积分、兑换数量、收货信息快照。
- 报名申请必须保存活动名称和活动时间快照。
- 收藏记录建议保存活动标题、活动时间、活动封面快照。
- 审计日志必须保存目标对象可读标识，避免源数据改名后日志不可读。

## 6.18 状态变更责任边界

- 游客不触发业务状态变更。
- 志愿者触发：报名、取消报名、签到、签退、提交认证、发帖、评论、收藏、兑换。
- 管理员触发：发布、归档、审核、下架、订单状态修改。
- 系统触发：活动结束、统计汇总、满足条件后的积分发放。
- 同一状态变化必须有明确主责任入口，禁止多角色无边界改同一状态。

## 6.19 旧数据回填策略

- 老活动积分默认补 `0`。
- 老报名理由默认补“历史数据未记录报名理由”。
- 老动态来源默认补“平台发布”或“历史数据”。
- 老帖子缺封面时补默认封面，缺摘要时由正文截断生成。
- 老用户积分默认补 `0`。
- 老订单缺快照字段时标记为“历史订单”并尽量保留已知信息。
- 老认证数据不存在时默认为 `UNSUBMITTED`。
- 老收藏缺快照时通过迁移或惰性补齐。
