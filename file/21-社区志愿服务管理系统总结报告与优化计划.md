# 社区志愿服务管理系统总结报告与优化计划

更新时间：2026-03-14

## 1. 执行摘要

本项目当前已经形成了可运行的前后端分离基线，业务主线明确围绕“社区志愿服务管理”展开，核心覆盖管理员治理、门户展示、志愿者自助、活动报名审核、签到签退、论坛互动、积分兑换、统计看板与审计留痕。

2026-03-14 已完成的本地验证结果如下：

- 前端单元测试通过：`Frontend -> npm run test:unit`
- 前端生产构建通过：`Frontend -> npm run build`
- 后端测试通过：`backend -> mvn test`
- 后端打包通过：`backend -> mvn -DskipTests package`

本轮同时完成了两项直接收口动作：

- 管理员首页删减非必要说明型内容，只保留核心指标、关键待办、图表趋势和快捷入口。
- 富文本编辑器扩充了标题层级、删除线、分隔线等格式能力，并统一了工具栏布局与清洗白名单。

整体判断：

- 架构方向是对的。
- 技术选型是稳定的。
- 代码与文档已经具备继续收口和优化的基础。
- 当前最大的风险不在“缺少新页面”，而在“边界持续被大页面、大文档、大杂烩模块稀释”。

## 2. 当前真实基线

### 2.1 业务定位

系统唯一核心应固定为：社区志愿服务管理系统。

围绕这个核心，当前三类前台角色与一类平台治理能力已经基本成形：

| 边界 | 当前职责 | 必须坚持的边界 |
| --- | --- | --- |
| 门户端 | 活动、资讯、公告、论坛公开浏览 | 只负责公开信息入口，不承载后台治理能力 |
| 志愿者端 | 报名、签到签退、收藏、评论、发帖、个人中心、认证、自助记录 | 只负责个人服务执行与自助查询 |
| 管理员端 | 活动治理、审核、内容管理、用户治理、统计、审计 | 只负责治理与审核，不回流到门户式展示 |
| 公共平台能力 | 认证鉴权、上传、统一错误处理、审计日志、数据迁移 | 只做平台基础能力，不夹带页面职责 |

### 2.2 技术基线

后端：

- Java 21
- Spring Boot 3.5.11
- Spring Security + JWT
- MyBatis-Plus 3.5.16
- Flyway
- SpringDoc OpenAPI

前端：

- Vue 3
- TypeScript
- Vite 8
- Element Plus
- Pinia
- Vue Router
- Axios / Day.js / ECharts / Playwright / Vitest

这套技术栈满足“最新且稳定”的要求，当前没有必要推倒重来。优化重点应放在边界治理、结构收口、编码质量、文档治理和自动化验证，而不是无效换栈。

### 2.3 已经形成的优势

- 前后端目录边界已经明确：`Frontend/` 与 `backend/` 分离。
- Flyway 迁移边界已建立，数据库结构变更不再依赖运行期 SQL 初始化。
- 管理端、门户端、志愿者端已经有统一设计令牌和共享组件基础。
- 部分重复逻辑已开始下沉到 `utils/`、`composables/`、共享组件。
- 审计日志、周榜、活动状态流转等关键治理能力已落地。
- 前端单测、后端测试、构建打包都已具备基础能力。

## 3. 当前主要问题与风险

以下问题按治理优先级排序，而不是按“看起来是否显眼”排序。

### 3.1 P0：后台功能边界仍有“大杂烩”倾向

当前 [ContentManageView](/f:/zero/Frontend/src/views/content/ContentManageView.vue) 在一个页面中同时承载：

- 信息动态
- 系统公告
- 轮播图
- 帖子分类
- 帖子审核
- 评论管理
- 积分商城
- 兑换订单

这会直接造成三个问题：

- 页面职责过宽，管理员认知负担过高。
- 内容治理与商城订单治理混在一起，不符合“该干什么就干什么”的原则。
- 路由通过 `tab` 复用一个大页面，不利于权限、文档、测试和后续统计收口。

结论：

- 这是后续必须拆分的重点。
- 不建议继续向 `content-manage` 继续塞新标签。

### 3.2 P0：文档体系过重，滚动记录过长

当前 `file/12`、`file/13`、`file/20` 等文档承载了大量阶段执行日志、治理记录和状态说明。优点是历史完整，缺点是：

- 当前有效结论不够聚焦。
- 新成员很难快速建立真实认知。
- 文档之间存在交叉、重复与“记录型内容盖过结论型内容”的问题。

结论：

- 后续必须保留“少量主文档 + 历史归档”结构。
- 运行规则、部署、边界、计划、验收结论必须分开，不再在一个文件里混写。

### 3.3 P0：跨机器运行基线还不够“一键化”

虽然本机已经可以完成前后端测试与打包，但距离“换一台电脑即可稳定运行”还有差距：

- 依赖仍主要靠人工安装和手工配置。
- 前端冒烟脚本依赖本地服务先启动。
- 数据库初始化和本地联调仍偏手工。
- 生产配置与开发配置的边界还需要更明确地模板化。

结论：

- 后续必须补齐 `.env.example` / 启动脚本 / 容器化或一键依赖编排方案。

### 3.4 P1：管理员首页、部分大页面仍有“说明书式堆叠”问题

虽然本轮已经收缩了 [AdminDashboardView](/f:/zero/Frontend/src/views/dashboard/AdminDashboardView.vue)，但从整体趋势看，后台页面依然容易出现：

- 首页承载过多说明型内容
- 大页面既做导航又做说明又做操作
- 页面中混合“入口、指标、说明、规则、日志、列表、弹窗”

结论：

- 后台首页只保留“判断 + 入口 + 待办 + 最近动作”。
- 说明文档应该下沉到对应模块文档，而不是塞在页面。

### 3.5 P1：富文本能力此前偏弱，展示与编辑规范仍需继续统一

本轮已经补齐了 [RichTextEditor.vue](/f:/zero/Frontend/src/components/shared/RichTextEditor.vue) 的更多格式能力，并同步扩展了 [rich-text.ts](/f:/zero/Frontend/src/utils/rich-text.ts) 的安全白名单。但从产品角度看，仍存在后续优化空间：

- 内容展示页对富文本的统一渲染规范还不够集中。
- 目前富文本仍然基于 `contenteditable + execCommand`，长期可维护性一般。
- 编辑器能力已经可用，但如果后续继续扩展附件、表格、引用块模板等，建议引入更明确的编辑模型。

结论：

- 当前版本以“稳定可用”为主。
- 长期建议评估更现代、可控的编辑器方案，但不建议立刻替换。

### 3.6 P1：代码结构已开始收口，但仍有进一步瘦身空间

当前重复代码问题主要集中在：

- 后台多页面的 CRUD 表格与弹窗表单模式
- 大页面通过 query tab 管理多个异质子模块
- 部分字符串、状态映射、页面说明与路由描述分散
- 文档与任务记录过量堆积

结论：

- 下一阶段要优先做“继续下沉共享能力 + 拆分大页面 + 收缩目录与文档”。

### 3.7 P1：配置治理还需要更严格

从 [application.yml](/f:/zero/backend/src/main/resources/application.yml) 可以看到：

- `app.jwt.secret` 仍然在仓库默认配置中直接给出。
- `mybatis-plus.configuration.log-impl` 在基础配置里启用了 SQL 控制台输出。

这在开发环境可接受，但对长期治理不理想。

结论：

- JWT 密钥应通过环境变量或外部配置注入，仓库只保留示例值。
- SQL 日志输出建议下沉到 `dev` profile，避免默认噪音。

### 3.8 P2：部分文档/终端读取存在编码表现不稳定

本次在终端盘点时，部分文档和个别源码文件读取时出现中文乱码表现，尤其体现在：

- `file/03-结构和配置文档.md`
- `file/07-前后端分离结构说明.md`
- `file/14-1-UI规范手册.md`
- `file/20-下一阶段功能补全开发计划.md`

结论：

- 必须统一仓库文本文件编码为 UTF-8。
- 同时补一轮编码检查脚本，避免再出现“页面正常、文档乱码、终端不稳定”的混合状态。

## 4. 必须长期坚持的治理原则

### 4.1 业务核心原则

- 所有功能、页面、命名、文档、统计、导航都必须围绕“社区志愿服务管理”。
- 不引入与主业务无关的娱乐化功能、泛社区功能或展示性噱头。

### 4.2 前后端分离原则

前端只负责：

- 页面展示
- 状态管理
- 表单交互
- 路由与权限前置保护
- 调用后端 API

后端只负责：

- 接口协议
- 鉴权与授权
- 业务规则
- 状态机与校验
- 数据访问与事务
- 审计、定时任务、迁移

禁止：

- 前端拼接后端业务规则
- 后端返回面向某个具体页面的耦合型结构
- 跨层硬编码重复状态语义

### 4.3 功能边界原则

- 一个页面只承担一个主要业务职责。
- 一个模块只聚合强相关能力，不做“顺手加进去”的入口堆叠。
- 管理端首页不是文档页，不是全功能导航页，也不是大屏页。
- 内容治理、论坛治理、商城订单治理不应长期共处于同一标签容器。

### 4.4 风格统一原则

- 继续以 `tokens.css + theme.css + element-overrides.css + shared components` 为统一来源。
- 统一布局、按钮、空态、确认链路、表单、分页、状态标签。
- 新页面不得重新发明并行视觉系统。

### 4.5 代码瘦身原则

- 优先删除重复、无效、历史遗留结构，而不是继续叠加新层。
- 大页面优先拆分成明确职责的模块页面。
- 重复的选择、确认、分页、状态提示、上传、富文本展示能力继续下沉。

### 4.6 文档治理原则

- 只保留必要且有用的文档。
- “规则型文档”和“过程型日志”必须分离。
- 当前有效规范必须能够在 5 分钟内被新开发者找到。

### 4.7 Skill 优先原则

- 开发、排障、联调、验证、文档处理、总结归档时，必须优先并积极使用已有 skill。
- 只要当前任务存在匹配 skill，就不允许跳过 skill 直接重复手工流程。
- skill 的使用要服务于“社区志愿服务管理系统”主链路，不为堆积工具而安装或启用无关能力。

### 4.8 验证优先原则

- 每轮开发必须同步验证前端单测、前端构建、后端测试、后端打包。
- 涉及关键链路的改动，必须补自动化验证。
- 烟雾测试不应依赖“开发者记得先手动启动一堆服务”。

## 5. 建议的目标结构

### 5.1 管理端目标边界

建议将当前管理员能力收口为以下明确入口：

| 模块 | 建议职责 |
| --- | --- |
| 系统首页 | 核心指标、关键待办、趋势图、最近操作 |
| 活动治理 | 活动分类、活动管理、报名审核、签到记录 |
| 内容治理 | 动态、公告、轮播图 |
| 论坛治理 | 帖子分类、帖子审核、评论管理 |
| 商城治理 | 商城商品、兑换订单 |
| 用户治理 | 志愿者、管理员、认证审核 |
| 系统设置 | 参数配置、后续通知与上传规则配置 |

重点：

- 取消“一个内容管理页面承载所有运营数据”的继续扩张。
- 后台导航改为按业务域拆分，而不是按技术实现习惯堆标签。

### 5.2 志愿者端目标边界

- 我的服务首页
- 报名申请
- 打卡记录
- 兑换订单
- 我的帖子 / 评论 / 收藏
- 个人中心 / 安全设置 / 认证信息

重点：

- 志愿者端只承载自助执行和个人记录，不出现后台式治理入口。

### 5.3 门户端目标边界

- 首页
- 活动
- 资讯动态
- 公告
- 论坛
- 商城

重点：

- 门户端只做公开入口与转化入口。
- 所有需要登录的动作统一回到登录后链路，不直接堆治理信息。

## 6. 分阶段优化计划

### 第一阶段：边界收口与编码治理

目标：先把最影响系统稳定性和理解成本的问题关掉。

执行项：

1. 拆分 `content-manage` 大标签页，至少拆为“内容治理 / 论坛治理 / 商城治理”三类路由。
2. 对后台导航和页面标题做一次业务域校正，避免重复指向和模糊命名。
3. 统一排查 UTF-8 编码问题，补一个编码扫描脚本并纳入日常验证。
4. 将仓库默认 JWT 密钥改成环境变量读取，仓库内仅保留示例。
5. 把 SQL 控制台日志配置移入 `dev` profile。

验收标准：

- 后台导航按业务域清晰可见。
- 不再新增 query-tab 巨型页面。
- 文档和源码终端读取不再出现明显乱码。

### 第二阶段：共享能力继续下沉

目标：减少重复代码和重复页面结构。

执行项：

1. 管理端 CRUD 页面继续统一表格骨架、抽屉/弹窗表单、分页、批量操作确认。
2. 富文本“编辑”和“展示”能力分离，增加统一的只读渲染容器。
3. 将常见状态映射、文案映射、标签颜色映射统一收敛。
4. 对上传、图片预览、表单校验规则做二次抽象。

验收标准：

- 新增同类页面不再手写一套完整骨架。
- 富文本在编辑页和展示页的视觉表现保持一致。

### 第三阶段：接口契约与自动化验证强化

目标：保证功能边界正确、接口稳定、回归可控。

执行项：

1. 为活动、报名、帖子、认证、订单补齐状态机回归测试。
2. 为游客 / 志愿者 / 管理员的页面路由与接口权限补齐边界测试。
3. 将关键烟雾链路升级为“前后端启动后可一键执行”的标准脚本。
4. 在构建链路中固定执行：
   - 前端单测
   - 前端构建
   - 后端测试
   - 后端打包

验收标准：

- 关键主链路具备自动回归能力。
- 角色边界回归失败时能及时暴露。

### 第四阶段：跨机器运行与部署基线固化

目标：确保在其它电脑上也能稳定运行。

执行项：

1. 补 `.env.example`、`application-prod.example.yml`、前端环境变量示例。
2. 增加统一启动说明和一键初始化脚本。
3. 评估并补齐 `docker-compose` 开发联调方案。
4. 固化 `MySQL + backend + Frontend/Nginx` 的标准联调拓扑。

验收标准：

- 新机器按文档能完成启动。
- 不依赖口头配置记忆。
- 本地与部署环境差异可控。

### 第五阶段：文档瘦身与治理固化

目标：让文档真正服务开发，而不是制造噪音。

执行项：

1. 保留以下主文档：
   - 开发文档
   - 接口文档
   - 结构与配置文档
   - 系统设计文档
   - 部署文档
   - UI 规范手册
   - 当前阶段优化计划
   - 当前阶段验收报告
2. 将长篇阶段执行日志转移为归档文件，不再作为当前主入口。
3. 每次迭代只更新与本轮直接相关的主文档。

验收标准：

- 新成员可在短时间内找到真实有效的规则、启动方式、边界说明和验收口径。

## 7. 建议的验收基线

后续每轮开发建议固定执行以下检查：

### 7.1 前端

- `npm run test:unit`
- `npm run build`
- 必要时执行 `npm run smoke:check`
- 关键链路改动执行 `node scripts/smoke-flow.mjs`

### 7.2 后端

- `mvn test`
- `mvn -DskipTests package`
- 关键状态机与权限改动补针对性测试

### 7.3 联调

- 游客访问门户公开页
- 志愿者登录、报名、签到签退、评论、兑换
- 管理员审核、归档/恢复、订单状态流转、审计日志

### 7.4 发布前

- Flyway 迁移校验
- UTF-8 编码校验
- 上传目录与静态资源路径校验
- 环境变量与默认密钥校验

## 8. 本轮建议结论

项目不需要重做。

项目需要的是：

- 更严格的业务边界
- 更少的大杂烩页面
- 更少的重复代码
- 更少的过程型文档噪音
- 更强的自动化验证
- 更稳定的跨机器启动基线

如果后续严格按本计划推进，系统可以在不换栈、不推翻现有成果的前提下，逐步收口为一个结构清晰、风格统一、边界明确、可持续迭代的社区志愿服务管理系统。

## 9. 建议新增的功能

### 9.1 志愿服务时长证明 / 电子证书

- 目标：让志愿者按月份、季度、年度导出服务时长证明或活动参与证明，减少线下人工开具。
- 前端建议：
  - 志愿者端新增“服务证明”入口，只负责筛选时间范围、预览和下载。
  - 管理员端只保留证明真伪核验入口，不重复提供志愿者自助导出页面。
- 后端建议：
  - 新增服务时长汇总接口和证明导出接口，统一读取签到签退记录与活动完成状态。
  - 证明编号、导出记录和模板参数由后端统一生成，前端不拼接业务规则。

### 9.2 平台通知中心

- 目标：把报名审核结果、活动开始提醒、签到提醒、认证审核结果、订单履约状态统一沉淀到“通知中心”，减少用户靠列表猜状态。
- 前端建议：
  - 门户端 / 志愿者端新增未读通知入口和通知列表页。
  - 管理端只保留通知模板与发送策略配置，不直接承载用户阅读界面。
- 后端建议：
  - 增加站内通知表、已读状态表和通知投递服务。
  - 由活动、认证、订单、论坛审核等模块通过事件或统一服务写入通知，避免各模块各自拼消息。

### 9.3 活动岗位与班次细化

- 目标：一个志愿活动下支持多个岗位或班次，例如签到引导、秩序维护、后勤保障，避免单活动单名额模型过粗。
- 前端建议：
  - 活动详情页只展示岗位、剩余名额、服务时段和报名入口。
  - 管理端活动编辑页增加岗位/班次配置区域，不把报名审核规则写在前端。
- 后端建议：
  - 在活动聚合下新增岗位/班次子表，报名记录绑定具体岗位。
  - 报名、签到、统计全部按岗位维度聚合，保持数据闭环。

### 9.4 志愿者成长档案

- 目标：沉淀个人累计时长、参与活动数、获得积分、历史荣誉、年度服务摘要，增强志愿者端的长期留存。
- 前端建议：
  - 放在志愿者自助体系内，作为“我的服务”或“个人中心”的下级能力。
  - 不进入门户端公开展示，避免把个人档案做成公共社交资料页。
- 后端建议：
  - 汇总活动记录、打卡记录、积分变更记录、认证记录，形成单独档案视图接口。
  - 只提供查询聚合结果，不把统计逻辑散落到多个控制器里。

### 9.5 活动异常签到预警

- 目标：对超距签到、异常时间签到、重复签到尝试形成异常标记，降低签到链路失真风险。
- 前端建议：
  - 管理端打卡记录页增加异常状态筛选和异常原因展示。
  - 志愿者端只展示自己的签到结果与失败原因，不暴露后台判定规则细节。
- 后端建议：
  - 在现有签到记录基础上补充异常标签字段和异常判定规则。
  - 判定逻辑归后端，前端只消费结果字段和说明文案。

### 9.6 数据导出中心

- 目标：把活动、报名、签到、认证、论坛审核、积分订单等导出能力统一收口，避免每个列表页都单独拼导出。
- 前端建议：
  - 管理端新增“导出中心”页，按业务域选择导出模板、筛选条件和时间范围。
  - 列表页保留“去导出中心”入口，不继续堆叠导出按钮。
- 后端建议：
  - 统一导出任务接口、下载记录和任务状态查询接口。
  - 导出模板按活动治理、内容治理、用户治理三个域拆分，避免杂糅。

## 10. 建议优先优化的现有功能

### 10.1 拆分内容管理大页面

- 当前问题：[ContentManageView.vue](/f:/zero/Frontend/src/views/content/ContentManageView.vue#L1) 仍用一个页面承载动态、公告、轮播、论坛、商城、订单八类内容。
- 优化建议：
  - 拆成“内容治理 / 论坛治理 / 商城治理”三条独立路由。
  - `admin-navigation.ts` 中对应入口从 query-tab 改成明确路由，权限、面包屑、文档和测试都按模块收口。

### 10.2 继续收缩管理员首页

- 当前问题：[AdminDashboardView.vue](/f:/zero/Frontend/src/views/dashboard/AdminDashboardView.vue#L3) 已明显收敛，但首页仍同时承载图表、待办、快捷入口和日志表格。
- 优化建议：
  - 首页长期固定为“核心指标 + 待办 + 最近动作”。
  - 趋势图表独立迁移到统计分析页，操作日志独立迁移到审计页，避免首页再次膨胀。

### 10.3 富文本“编辑”和“展示”彻底分层

- 当前问题：[RichTextEditor.vue](/f:/zero/Frontend/src/components/shared/RichTextEditor.vue#L2) 已扩展工具栏并统一布局，但展示侧还没有完全形成统一只读渲染容器。
- 优化建议：
  - 增加共享 `RichTextContent` 或 `RichTextRenderer` 组件，所有动态、公告、活动详情、帖子详情统一使用。
  - 编辑器继续保留当前稳定方案，展示层统一样式、图片边界、标题间距、引用块和空内容兜底。

### 10.4 管理端导航按业务域继续瘦身

- 当前问题：[admin-navigation.ts](/f:/zero/Frontend/src/constants/admin-navigation.ts#L48) 虽已分组，但“信息管理”仍聚合活动、内容、论坛、商城、订单多个异质域。
- 优化建议：
  - 改为“系统首页 / 活动治理 / 内容治理 / 用户治理 / 系统设置”五组。
  - 导航命名与路由、接口文档、测试用例保持完全一致，减少重复指向和模糊入口。

### 10.5 跨机器运行基线补齐模板化能力

- 当前问题：项目可以在本机跑通，但跨机器仍依赖手工安装与口头约定。
- 优化建议：
  - 增加 `.env.example`、`application-prod.example.yml`、前端环境变量示例和一键启动脚本。
  - 补一套 `docker-compose` 本地联调基线，至少覆盖 `MySQL + backend + Frontend/Nginx`。

### 10.6 配置与密钥治理收严

- 当前问题：JWT 密钥和 SQL 日志开关仍偏靠基础配置硬编码。
- 优化建议：
  - 敏感配置全部外置，仓库只保留示例值与说明。
  - SQL 调试日志下沉到 `dev` profile，避免默认输出污染运行日志和其他环境。

### 10.7 权限与状态机回归测试加强

- 当前问题：系统已经有角色边界和状态流转，但后续继续增量开发时容易回归。
- 优化建议：
  - 围绕报名审核、认证审核、帖子审核、订单状态流转建立固定回归矩阵。
  - 前端侧补路由守卫与菜单可见性测试，后端侧补角色拒绝与非法状态迁移测试。

### 10.8 UTF-8 编码治理常态化

- 当前问题：部分文档和终端读取仍会出现中文乱码表现，影响跨机器协作。
- 优化建议：
  - 为仓库增加编码扫描脚本和提交前检查。
  - 新增文档统一采用 UTF-8，无 BOM 或是否带 BOM 需要在仓库中统一，不允许混用。

## 11. 规划阶段实施顺序

当前阶段判断为“规划阶段”，不继续扩散实现范围，先固定后续实施顺序，避免再次回到“想到什么就往现有大页面里补什么”的模式。

建议按以下顺序推进：

1. 先做后台业务域拆分与配置治理。
2. 再做通知中心、服务证明、导出中心三项高价值新增能力。
3. 最后再评估岗位 / 班次、异常签到、成长档案等增强型能力。

原因：

- 后台结构不先拆开，新功能只会继续堆到现有管理大页中。
- 配置、编码、回归基线不先收紧，新增功能越多，后续维护成本越高。
- 通知、证明、导出更贴近当前主业务闭环，收益明显高于社交化扩展。

## 12. 规划阶段明确停做与删减建议

以下事项建议从当前规划中明确列为“停止继续扩张”或“仅保留兼容，不再增强”：

### 12.1 停止继续向内容管理大页面叠加标签页

- 不再向 `ContentManageView` 继续新增 tab。
- 现有动态、公告、轮播图、帖子分类、帖子审核、评论、商城商品、订单应逐步拆向独立业务域页面。
- `content-manage` 只作为过渡兼容入口保留一个阶段，后续移除。

### 12.2 停止把管理员首页继续做成综合信息墙

- 首页不再新增说明性文字、大段规则提示、低频入口和额外运营模块。
- 首页长期只保留：
  - 核心指标
  - 待处理事项
  - 最近动作
- 趋势图、审计日志、统计分析等拆到独立页面更符合治理边界。

### 12.3 停止引入与主业务弱相关的泛社区能力

- 当前不建议扩展聊天、点赞排名、社交广场、个性装扮等功能。
- 当前也不建议继续强化“公开社交资料页”方向。
- 系统应持续围绕“社区志愿服务管理”而不是“泛社区互动平台”收口。

### 12.4 旧兼容入口只保留跳转，不作为长期结构

- `/volunteer/*` 当前仅作为兼容路由，不再承载新功能。
- `/admin/content-manage?tab=*` 当前仅作为兼容访问方式，不再作为长期后台主入口。
- 后续应通过埋点或访问统计确认无依赖后再移除。

### 12.5 不建议短期更换富文本技术栈

- 当前编辑器已经达到“稳定可用”状态。
- 短期收益更高的工作仍然是页面拆分、展示统一和回归补强。
- 因此短期不建议在未完成结构收口前引入新编辑器框架。

## 13. 规划阶段拟调整的路由、接口与数据模型

本节用于给后续实施提供明确的规划基线，当前为规划结论，不代表本轮已经实现。

### 13.1 路由调整建议

后台新增独立业务域路由：

- `/admin/content`
- `/admin/forum`
- `/admin/mall`
- `/admin/audit`
- `/admin/analytics`
- `/admin/export-center`

保留兼容跳转：

- `/admin/content-manage?tab=*` -> 对应新业务域路由

志愿者端新增：

- `/portal/me/notifications`
- `/portal/me/certificates`

路由原则：

- 所有新路由按业务域命名，不再按“一个大页面 + tab 参数”表达模块边界。
- 管理端导航、页面标题、面包屑、测试命名和文档命名都必须使用同一套业务域术语。

### 13.2 接口规划建议

通知中心：

- `GET /api/notifications/page`
- `POST /api/notifications/{id}/read`
- `POST /api/notifications/read-all`

志愿服务证明：

- `GET /api/users/me/service-summary`
- `POST /api/certificates/export`
- `GET /api/certificates/{id}/verify`

导出中心：

- `POST /api/export-tasks`
- `GET /api/export-tasks/page`
- `GET /api/export-tasks/{id}`

接口原则：

- 前端只负责筛选、展示和下载，不拼接业务规则。
- 编号生成、模板参数、导出状态和通知投递都应由后端统一控制。
- 不重写现有活动、报名、认证、订单基础状态机。

### 13.3 数据模型规划建议

建议新增以下模型：

- `Notification`
- `NotificationReadState`
- `ServiceCertificate`
- `ExportTask`

后续如活动复杂度继续提高，再进入下一阶段评估：

- `ActivitySlot`
- `ActivityShift`

当前不建议在未完成结构收口前提前引入岗位 / 班次模型。

## 16. 可继续补充的优化建议

前文主要聚焦于“结构拆分、功能增减、规划顺序”。如果继续往下细化，下一层真正影响系统质量的点主要集中在业务一致性、使用体验、性能稳定性、安全合规和运维交付五个方面。

### 16.1 业务一致性治理

当前系统已经具备活动、报名、签到、认证、积分订单、论坛审核等主链路，但仍建议继续做以下一致性收口：

- 统一“统计口径”的来源定义。
  - 后台首页、统计分析页、列表分页总数、门户展示数量、自助记录数量必须使用同一套数据口径。
  - 归档、停用、待审核、已完成等状态是否计入统计，应形成书面规则，不允许页面各自解释。
- 统一“待办数量”的聚合来源。
  - 报名待审核、帖子待审核、认证待审核、待履约订单建议统一从后端聚合接口返回。
  - 不建议前端各页面自行拼接多个接口后再临时算“待办”。
- 统一“历史记录”的展示语义。
  - 活动改名、公告下线、商品下架之后，历史报名、订单、收藏、导出记录应保留当时快照语义。
  - 避免详情页、记录页和后台页对同一条历史数据显示不同名字或状态。
- 统一“批量操作”的行为口径。
  - 批量归档、批量恢复、批量停用、批量删除应统一要求确认、结果反馈、失败项说明和审计留痕。

### 16.2 使用体验优化

建议在不增加花哨能力的前提下，继续改善用户真正高频使用的体验：

- 志愿者端增加“状态时间线”表达。
  - 报名记录页可以明确显示：已提交 -> 已审核 -> 已签到 -> 已签退 / 未完成。
  - 认证记录、订单记录也建议增加状态时间线或关键时间节点。
- 把“待我处理”与“最近变化”明确分开。
  - 管理员首页只放待办；已完成动作和审计历史应进入审计中心。
  - 志愿者首页只放与本人相关的提醒，不堆管理口径信息。
- 搜索与筛选结果应可回显、可复用。
  - 管理端高频列表页建议保留当前筛选条件、分页位置和查询关键词。
  - 避免管理员点进详情再返回时丢失筛选上下文。
- 强化空态与错误态表达。
  - 空态不仅提示“暂无数据”，还应明确“为什么为空”和“下一步可以做什么”。
  - 错误态建议区分网络问题、权限问题、数据不存在和状态已变更。

### 16.3 性能与稳定性优化

当前前后端已经能稳定构建和测试，但仍可继续做以下优化：

- 后台拆分后按业务域做路由级懒加载。
  - 内容治理、论坛治理、商城治理分开后，避免后台首次进入就加载全部管理子模块。
- 对门户首页和志愿者首页的聚合接口做轻量化。
  - 首页接口只返回首页必须展示的数据，避免把详情页所需字段全部塞入首页返回。
- 对图片和富文本内容做加载控制。
  - 门户图、帖子封面、活动封面建议统一压缩、懒加载和兜底图策略。
  - 富文本详情页建议限制超大图片宽度和异常内容渲染。
- 对高频分页查询补数据库层优化。
  - 活动分页、帖子分页、评论分页、订单分页、通知分页等高频列表应逐步复核索引与查询字段组合。
  - 统计和列表若共享重查询逻辑，应评估是否需要只读聚合视图或缓存策略。

### 16.4 安全与合规优化

除 JWT 密钥和 SQL 日志治理外，还建议继续收严以下边界：

- 上传资源分类分级管理。
  - 普通公开图片、后台管理图片、身份证图片、导出文件应分目录、分访问策略。
  - 身份证图片、证明文件、导出结果不应匿名直链访问。
- 强化账号与密码策略。
  - 默认账号只允许在开发环境保留，部署前必须强制变更。
  - 增加密码强度、登录失败限制、敏感操作二次确认等策略。
- 审计日志补足“失败原因”和“操作者意图”。
  - 对驳回审核、订单取消、批量停用、恢复发布等操作，建议记录原因字段。
  - 这样后续复盘时能知道“做了什么”以及“为什么这么做”。
- 导出与证明类能力默认按权限最小化开放。
  - 志愿者只能查看自己的证明与通知。
  - 管理员导出应按业务域和角色授权，不应默认开放全量数据导出。

### 16.5 运维与交付优化

如果目标是“换机器也能稳定运行”，建议补齐以下交付能力：

- 增加健康检查和依赖自检。
  - 后端提供基础健康检查入口。
  - 启动脚本可在前置阶段检查数据库连接、上传目录、环境变量是否缺失。
- 增加标准初始化脚本和标准清理脚本。
  - 包括开发库初始化、测试数据清理、冒烟前置准备、导出目录清理等。
- 增加“最小演示数据”方案。
  - 新开发者拉起系统后，应能快速看到一套可浏览、可登录、可演示的最小数据。
- 固化发布前检查清单。
  - Flyway、环境变量、默认账号、上传目录权限、日志级别、默认密钥、编码检查等应形成固定发布前检查项。

## 17. 下一轮更具体的改进方案

如果需要把当前文档进一步落为下一轮任务单，建议把后续工作拆成以下几片，而不是继续大包推进：

### 17.1 J1 后台业务域路由正式拆分

## 18. 建议补充的量化目标

为了避免“做了很多优化，但很难判断是否真的变好”，建议在后续迭代中为核心优化项增加量化目标：

- 后台首屏入口数量减少到可控范围，避免一个分组承载过多异质业务。
- 核心高频页面首屏接口数量下降，减少无效并发请求。
- 关键主链路全部具备最小自动化回归。
- 新开发者按文档从零启动项目的时间缩短到可接受范围。
- 编码、密钥、环境变量、Flyway 等基础治理项进入固定检查链路，不再依赖人工记忆。

这些目标不要求一次全部完成，但应成为后续每轮优化是否真正有效的判断标准。

## 19. 建议的优先级矩阵

为了避免优化项越来越多但执行顺序越来越乱，建议后续所有事项统一放入以下四象限判断：

### 19.1 P0：高收益、强依赖、必须先做

这类事项不先处理，后续功能越做越乱：

- 后台业务域拆分
- 管理端导航收口
- JWT / 环境变量 / 日志配置治理
- UTF-8 编码治理
- 权限边界与状态机回归补强
- 跨机器启动基线和一键化说明

执行原则：

- 优先安排到最近一轮迭代。
- 必须有明确验收标准。
- 未完成前不继续向旧结构叠加新模块。

### 19.2 P1：高收益、可快速形成闭环

这类事项能显著提升系统完成度和答辩说服力：

- 平台通知中心
- 志愿服务证明
- 导出中心
- 审计中心独立
- 富文本展示统一容器

执行原则：

- 在 P0 项稳定后立即推进。
- 每次只做一个最小闭环，不并发扩散。

### 19.3 P2：中期增强能力

这类事项价值明确，但不应抢占当前主线：

- 活动岗位 / 班次
- 异常签到预警
- 志愿者成长档案
- 统计分析页扩展
- 通知模板与发送策略配置

执行原则：

- 仅在主链路和结构治理稳定后启动。
- 启动前先补业务边界和数据模型说明。

### 19.4 P3：当前不建议投入

这类方向当前收益偏低，且容易稀释主业务：

- 聊天、即时消息、私信系统
- 点赞排名、社交广场、个性化装扮
- 与志愿服务主闭环弱相关的娱乐化功能
- 为了“看起来更高级”而做的大屏化改造

执行原则：

- 当前阶段明确不排期。
- 若未来确有需求，必须重新论证是否偏离“社区志愿服务管理”主目标。

## 20. 主要风险与应对方案

优化项明确之后，还需要提前写清风险与处理方式，否则很容易在执行时反复回摆。

### 20.1 结构拆分风险

风险：

- 拆分后台路由和页面后，旧链接、菜单高亮、测试用例、说明文档可能全部失配。

应对：

- 保留兼容跳转期。
- 每拆一条业务域路由，就同步更新导航、文档和最小回归测试。
- 先拆入口，再拆页面内部组件，不一次性推翻。

### 20.2 新能力扩散风险

风险：

- 通知中心、导出中心、证明导出这类能力一旦范围失控，很容易从“最小闭环”膨胀成多端、多模板、多通道的大工程。

应对：

- 通知中心先只做站内通知，不并发做短信、邮件、微信。
- 证明导出先只做个人服务证明，不并发做复杂模板市场。
- 导出中心先只做后台管理导出，不并发做异步报表体系。

### 20.3 文档与实现脱节风险

风险：

- 规划越来越完整，但如果实现过程中不持续回写文档，后面会再次出现“文档写的是一套，代码跑的是一套”。

应对：

- 每一轮只更新与本轮直接相关的主文档。
- 每个切片结束后同步更新当前文档中的完成状态和后续优先级。
- 不再让过程型执行日志掩盖结论型文档。

### 20.4 回归范围失控风险

风险：

- 优化范围扩大后，测试和回归链路可能跟不上，最终只能靠手工验证。

应对：

- 每新增一类能力，都要求补至少一层自动化验证。
- 后台路由拆分必须同时补菜单、权限和兼容跳转回归。
- 新增通知、证明、导出时，不允许只做页面不做接口级回归。

## 21. 建议的实施里程碑与退出条件

为了让后续推进更稳定，建议把优化工作划成几个可以独立验收的里程碑。

### 21.1 里程碑 M1：后台结构收口

范围：

- 完成后台业务域导航拆分
- 完成旧 `content-manage` 兼容跳转
- 管理员首页完成瘦身
- 审计日志迁移出首页

退出条件：

- 管理员可通过新导航直接进入各业务域
- 首页不再承担大杂烩职责
- 旧入口仍能兼容访问

### 21.2 里程碑 M2：平台能力闭环

范围：

- 通知中心最小闭环
- 服务证明最小闭环
- 导出中心最小闭环

退出条件：

- 志愿者能查看通知并处理已读
- 志愿者能导出证明并完成核验
- 管理员能统一发起导出并查看任务状态

### 21.3 里程碑 M3：治理与交付基线固化

范围：

- 环境变量、默认密钥、日志配置收口
- UTF-8 编码检查
- 跨机器启动模板与联调方案
- 发布前检查清单固化

退出条件：

- 新机器可按文档完成最小启动
- 基础配置不再依赖口头说明
- 编码、密钥、环境变量检查进入固定流程

### 21.4 里程碑 M4：增强能力评估期

范围：

- 岗位 / 班次
- 异常签到预警
- 成长档案

退出条件：

- 仅在 M1-M3 稳定后再决定是否启动
- 启动前必须补业务说明、数据模型和验收标准

## 22. 建议主动清理的历史结构与技术债

除了新增和优化，还应明确哪些历史结构值得逐步清理，否则仓库会持续膨胀。

### 22.1 页面与路由层

- 长期移除 `/admin/content-manage?tab=*` 主入口地位
- 长期移除旧 `/volunteer/*` 功能入口
- 清理已经被独立页面替代的 query-tab 导航逻辑

### 22.2 文档层

- 将超长阶段日志转入归档目录
- 当前主文档只保留规则、结构、计划、验收和结论
- 清理重复表达相同事实的并行文档

### 22.3 配置层

- 清理仓库中的默认敏感值
- 清理默认环境下不必要的 SQL 控制台输出
- 清理“开发环境方便，但长期不安全”的默认开关

### 22.4 测试与脚本层

- 清理不再对应真实入口的老脚本和过时说明
- 把重复的验证流程收口到固定命令
- 对仅为某次排障临时引入的辅助产物做归档或删除

## 23. 建议补充的汇报表达重点

如果后续这份文档还需要服务于答辩、汇报或阶段评审，建议把优化成果统一归纳成以下几个表达重点：

- 系统不是简单“补页面”，而是在持续做业务边界收口。
- 当前优化重点不是换技术栈，而是提高结构清晰度、治理能力和可维护性。
- 新增功能优先围绕通知、证明、导出这类直接提升业务闭环的能力。
- 删除与停做同样重要，主动控制大杂烩页面和低收益功能扩张。
- 优化目标不仅是“能跑”，而是“可理解、可验证、可交付、可持续迭代”。

这样在后续沟通中，文档不仅能指导开发，也能解释为什么当前的优化方向是合理且克制的。

## 24. 数据库设计优化建议

在当前阶段，数据库层不建议推倒重建，但应继续围绕“结构清晰、状态明确、查询稳定、历史可追溯”四个方向做增量优化。

### 24.1 统一状态字段设计口径

当前系统已经存在活动、报名、签到、帖子、认证、订单等多类状态字段，后续建议继续统一以下规则：

- 状态字段优先使用可读枚举值或明确受控字符串，不再混用含义不稳定的数字状态。
- “归档 / 停用 / 删除别名 / 发布 / 审核中 / 审核通过 / 审核拒绝”应在表结构层明确语义，不使用同一个状态值承载多个业务含义。
- 所有状态迁移都应有固定入口，不允许通过直接更新数据库字段绕过状态机。

建议：

- 对现有核心表形成一份状态字段字典。
- 在文档中固定每张表允许的状态值、迁移方向和是否进入统计口径。

### 24.2 历史快照字段继续补齐

当前系统已经在收藏和订单等部分链路中引入快照语义，后续建议继续补齐：

- 报名记录应优先保留活动标题、活动时间、活动地点等关键快照。
- 订单记录应保留商品名称、图片、单价积分、收货信息等完整快照。
- 服务证明、通知记录、导出记录也应避免完全依赖实时主表回查。

这样做的价值：

- 避免主数据修改后污染历史记录语义。
- 保证导出、审计、统计、证明与历史页面展示一致。

### 24.3 审计与业务表解耦

建议继续坚持“业务表只记录业务事实，审计表记录操作过程”的原则：

- 不要把大量操作说明、失败原因、人工备注直接混塞进主业务表。
- 审核原因、恢复原因、取消原因、批量操作上下文等优先进入审计表或独立日志表。
- 对需要长期保留的人为说明，可保留在业务表中最小字段，但不应替代审计日志。

这样能避免：

- 业务表越来越臃肿
- 审计语义和业务语义混杂
- 后续统计与查询负担持续上升

### 24.4 高分页压力表建议补索引治理

随着后台治理能力增加，以下表的分页压力会持续上升：

- 活动表
- 报名表
- 签到记录表
- 帖子表
- 评论表
- 订单表
- 通知表
- 导出任务表

建议对高频查询组合逐步复核索引，例如：

- `status + create_time`
- `user_id + create_time`
- `activity_id + status`
- `target_type + target_id`
- `role + status`

原则：

- 只为真实高频过滤组合建索引，不为了“看起来完善”而滥建索引。
- 索引策略应以后台真实分页和筛选场景为依据。

### 24.5 大字段与列表字段分离

对于富文本、长说明、审计详情、导出参数等大字段，建议持续避免它们进入高频列表默认查询：

- 活动正文、动态正文、公告正文、帖子正文应与列表展示字段逻辑上分离。
- 导出任务的参数 JSON、结果文件路径、错误详情可单独管理，避免影响列表页性能。
- 证明模板内容、通知模板内容如果后续增加，也应避免进入普通分页主查询。

目标：

- 让列表页只查询列表必需字段。
- 详情页再按需加载正文和大字段内容。

### 24.6 迁移治理继续保持“小步前进”

当前 Flyway 治理已经建立，后续建议保持以下纪律：

- 每次数据库变更只解决一个明确问题，不合并过多 unrelated 修改。
- 新增字段必须同步说明默认值、历史数据回填策略和是否影响统计。
- 删除或重命名字段必须先做兼容期，不直接破坏线上或历史环境。
- 任何涉及权限、审核、导出、证明、通知的数据结构改动，都应同步补迁移验证说明。

## 25. 接口设计优化建议

接口层已经具备统一响应结构，但为了支持后续通知、证明、导出和后台业务域拆分，建议继续做契约级优化。

### 25.1 接口按业务域继续收口

当前系统已有活动、内容、用户、统计等模块边界，后续建议继续坚持：

- 活动相关接口只负责活动、报名、签到及其直接聚合。
- 内容相关接口只负责动态、公告、论坛、商城等内容域能力。
- 用户相关接口只负责个人资料、认证、权限内自助查询。
- 新增通知、证明、导出能力时，不建议继续塞进现有大控制器中，应建立独立业务域入口。

建议新增的接口域：

- `notifications`
- `certificates`
- `exports`
- `audit` 或 `operations`

### 25.2 列表接口与详情接口职责分离

后续应继续明确：

- 列表接口只返回列表展示所需字段。
- 详情接口返回完整正文、扩展说明、审计上下文、富文本内容。
- 首页聚合接口只返回首页必要摘要，不回传大批详情字段。

这样可以减少：

- 前端过度依赖单个超大接口
- 无效字段传输
- 页面间契约耦合

### 25.3 聚合接口优先由后端提供

以下类型的数据不建议由前端自行聚合：

- 管理员首页待办统计
- 志愿者首页提醒数量
- 通知未读数
- 证明汇总统计
- 导出任务状态概览

原因：

- 前端自行聚合会造成多接口拼装、状态不一致和重复口径。
- 同一业务规则应只在后端统一实现一次。

### 25.4 批量操作接口语义继续统一

建议所有批量操作接口统一遵循类似语义：

- 明确动作名称：批量归档、批量恢复、批量停用、批量删除
- 明确输入载荷：统一 `ids`
- 明确失败反馈：应能知道是全成功、部分失败还是全失败
- 明确审计要求：批量操作必须可留痕

如后续需要增强，可进一步统一返回：

- 成功数量
- 失败数量
- 失败原因摘要

### 25.5 新增能力接口建议最小闭环优先

通知中心：

- 先只做分页、已读、全部已读三类能力
- 不先做复杂搜索、模板管理、多通道发送

服务证明：

- 先只做个人统计、导出、核验
- 不先做批量开具、多模板、多章样式编辑

导出中心：

- 先只做任务创建、状态查询、结果下载
- 不先做复杂报表编排和跨系统集成

### 25.6 错误码与失败信息继续标准化

当前统一错误码方向是正确的，后续建议继续补足：

- 通知不存在、证明不存在、导出任务不存在应有明确错误码。
- 非法状态迁移、非法角色访问、资源已归档、资源已停用等应继续使用稳定错误码而不是页面自行解释。
- 前端展示文案可以友好，但底层错误码必须稳定，方便测试和日志追踪。

### 25.7 接口版本与兼容策略建议

当前项目尚不一定需要复杂版本化，但建议提前明确兼容原则：

- 对旧路由、旧 query 参数、旧响应字段的移除，优先采用兼容期而不是立即删除。
- 当后台从 `content-manage` 拆为独立域后，兼容跳转和旧前端入口应保留一个过渡周期。
- 若后续响应字段需要调整，应优先“新增字段 -> 前端切换 -> 删除旧字段”的顺序，而不是直接替换。

目标是：

- 在持续优化的同时，保持联调稳定和测试可追踪。

## 26. 前端页面交互优化建议

前端当前已经建立了统一设计令牌、共享组件和基础交互规范，后续优化重点不应再是“继续堆页面”，而应放在交互一致性、操作可理解性和信息层级清晰度上。

### 26.1 列表页交互继续统一

后台和志愿者端的高频列表页，后续建议继续统一以下交互元素：

- 筛选区位置统一
- 主按钮与次按钮优先级统一
- 批量操作入口统一
- 分页区位置统一
- 空态、加载态、错误态统一

建议：

- 同类列表页优先复用同一套页面骨架和操作区布局。
- 不再允许某些页面“筛选在上、分页在下”，另一些页面“分页在中、操作在右”的并行风格长期共存。

### 26.2 危险操作交互继续收口

虽然当前部分危险操作已经接入统一确认链路，但后续仍建议继续强化：

- 归档、恢复、停用、删除、审核拒绝、订单取消等动作统一进入共享确认流程。
- 对需要填写原因的动作，统一采用“先输入原因，再确认”的交互模式。
- 对批量操作，明确展示“影响范围”和“不可逆程度”。

目标：

- 让管理员在执行危险操作时更容易理解后果。
- 减少页面级手写确认弹窗带来的行为不一致。

### 26.3 页面信息层级继续瘦身

后续页面优化建议继续坚持：

- 一个页面只服务一个主要任务。
- 页面顶部只保留必要标题、简短说明和主要动作。
- 大段规则说明、低频帮助说明、次要统计不直接堆在主操作页。

适用场景：

- 后台首页
- 内容治理页
- 论坛治理页
- 商城治理页
- 志愿者个人中心和服务记录页

### 26.4 状态表达可视化统一

建议继续统一状态标签、颜色、图标和时间线表达：

- 报名状态、帖子审核状态、认证状态、订单状态、签到状态统一使用共享映射。
- 对具备明确流程的业务，优先采用时间线或步骤表达，而不是只展示单个状态字。
- 历史状态和当前状态应有明确区分，不让用户误以为旧状态仍可操作。

### 26.5 详情页与列表页分层更清晰

后续前端应继续避免“列表页承担过多详情能力”的问题：

- 列表页只展示摘要和关键操作。
- 富文本正文、长说明、完整记录、历史详情进入独立详情页或抽屉。
- 列表页不再承载过长正文、复杂图片区和说明型内容。

### 26.6 志愿者端体验优化方向

志愿者端不建议继续后台化，而应更突出“个人服务台”体验：

- 首页更强调“我接下来要做什么”而不是“系统能做什么”。
- 报名记录、签到记录、订单记录、认证记录建议增加关键时间节点和结果说明。
- 通知、证明、成长档案这类能力应统一进入自助服务体系，而不是散落在多个入口。

### 26.7 门户端体验优化方向

门户端建议继续保持“公开浏览 + 转化入口”的定位：

- 首页只放活动、公告、资讯、论坛、商城等公开导流内容。
- 所有登录后动作统一引导到登录与自助链路。
- 不在门户端叠加后台式管理信息、复杂操作流程或个人治理入口。

## 27. 后端服务拆分与模块治理建议

后端目前已经开始做查询/命令职责拆分，这个方向是正确的，后续建议继续沿着“模块边界清晰、服务职责收敛、控制器轻量、规则集中”的方式推进。

### 27.1 控制器继续保持薄层

控制器层建议继续只承担：

- 参数接收
- 基础校验
- 角色入口控制
- 响应包装

不建议控制器继续承担：

- 复杂状态迁移判断
- 聚合统计拼装
- 审计细节拼接
- 多表业务决策

### 27.2 服务按业务域继续拆分

建议在现有活动、内容、用户、统计等模块上继续保持清晰边界：

- 活动域：活动、报名、签到、服务统计
- 内容域：动态、公告、论坛、轮播图
- 商城域：商品、订单、履约
- 用户域：个人信息、认证、账号状态
- 平台域：通知、导出、证明、审计

原则：

- 不再让一个大 Service 同时承担多个异质业务域。
- 新功能优先进入对应业务域，而不是回塞旧混合服务。

### 27.3 继续推进 Query / Command 分离

当前查询与写路径拆分已经在部分模块落地，后续建议继续深化：

- Query Service 专注分页、详情、聚合读取
- Command Service 专注创建、更新、审核、状态迁移、批量动作
- Facade Service 仅在需要时保留门面职责，不继续膨胀

这样能带来的收益：

- 查询行为更容易复用
- 写路径规则更容易测试
- 控制器与前端更容易理解服务职责

### 27.4 通知、证明、导出能力单独建域

这三类能力后续不建议挂靠在现有大模块下“顺手实现”，而应尽早形成独立域：

- 通知域：通知生成、分页、已读状态
- 证明域：服务统计、证明生成、核验
- 导出域：导出任务、模板、下载记录、状态管理

原因：

- 这三类能力会横跨活动、认证、订单等多个业务模块。
- 如果一开始就塞进活动或用户模块，后续边界会再次模糊。

### 27.5 统一平台能力下沉

以下能力建议继续集中抽象，而不是各模块重复实现：

- 当前登录用户获取
- 统一错误码
- 分页结果包装
- 审计日志写入
- 批量操作校验
- 上传规则校验
- 测试数据标记

目标：

- 把通用平台能力沉到公共层。
- 把真正的业务规则留在业务域内。

### 27.6 模块治理建议形成白名单与黑名单

建议在文档层继续明确：

白名单：

- 新模块必须有明确业务域归属
- 新接口必须有清晰权限边界
- 新状态字段必须有状态机说明
- 新导出 / 通知 / 证明能力必须同步补最小回归

黑名单：

- 不允许新增“万能大页面”
- 不允许新增“万能大 Service”
- 不允许继续在控制器堆业务逻辑
- 不允许绕开统一异常与审计体系

## 28. 测试体系与验收流程优化建议

当前项目已经具备前端单测、后端测试、构建、打包和部分冒烟基础，下一步重点应从“有测试”升级到“有分层、可回归、可验收”。

### 28.1 测试分层建议

后续建议把测试体系明确拆为四层：

- 单元测试：验证工具函数、状态映射、服务内部规则
- 契约测试：验证接口路径、响应字段、权限边界、错误码
- 集成测试：验证真实业务链路与状态迁移
- 冒烟测试：验证前后端联动下的关键用户路径

原则：

- 每一层解决的问题不同，不互相替代。
- 不应全部依赖最重的端到端测试。

### 28.2 关键链路回归矩阵建议

后续建议把以下链路固定为核心回归矩阵：

- 登录与角色边界
- 活动创建、报名、审核、签到、签退
- 帖子提交、审核、展示
- 认证提交、审核、结果可见性
- 订单创建、履约、取消、完成
- 通知生成、已读、全部已读
- 证明导出与核验
- 导出任务创建与下载

### 28.3 路由拆分后的前端回归要求

后台从 `content-manage` 拆分为独立业务域后，前端测试应同步覆盖：

- 新导航点击可达
- 旧 query-tab 兼容跳转仍可用
- 菜单高亮正确
- 页面标题和当前模块标题正确
- 无权限角色不能进入对应页面

### 28.4 发布前验收流程建议

后续每轮迭代在宣布“完成”前，建议固定执行以下验收顺序：

1. 前端单测
2. 前端构建
3. 后端测试
4. 后端打包
5. 关键链路冒烟
6. 编码检查
7. 环境变量与默认密钥检查
8. Flyway 迁移检查

这样可以避免：

- 代码改完但没构建
- 构建通过但接口契约已漂移
- 功能可用但环境基线不稳定

### 28.5 验收结论表达建议

后续每轮验收文档建议统一只回答四个问题：

- 本轮目标是什么
- 实际完成了什么
- 哪些验证已经通过
- 哪些风险或遗留问题仍未关闭

这样做的价值：

- 验收结论更清晰
- 阶段状态更容易追踪
- 不再让大量过程记录掩盖真正的完成情况
