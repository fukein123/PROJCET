# 深度重构观察报告

> 观察日期：2026-03-15
> 项目：社区志愿服务管理平台 (zero2.0)
> 技术栈：Java 21 + Spring Boot 3.5 + Vue 3 + MySQL 8

---

## 一、架构设计层面的问题

### 1. User 实体严重违反单一职责原则

**位置**：[User.java](../backend/src/main/java/com/community/modules/user/entity/User.java)

**问题描述**：
User 实体承载了过多职责，包含 8 个 `@TableField(exist = false)` 字段用于承载志愿者认证快照信息：
- `certificationId`
- `certificationStatus`
- `certificationRejectReason`
- `certificationIdCardNo`
- `certificationIdCardFrontUrl`
- `certificationIdCardBackUrl`
- `certificationSubmitTime`
- `certificationAuditTime`
- `certificationAuditorId`

**影响**：
- 实体类职责不清晰，混合了持久化和视图展示职责
- 如果未来需要展示更多关联信息，会导致 User 实体持续膨胀
- 违反单一职责原则，增加维护成本

**建议**：
- 创建专门的 `UserCertificationVO` 或 `UserDetailVO` 来承载视图层数据
- User 实体只保留数据库持久化字段

---

### 2. Service 层职责混乱，缺乏清晰的边界

**位置**：
- [ActivityService.java](../backend/src/main/java/com/community/modules/activity/service/ActivityService.java)
- [UserService.java](../backend/src/main/java/com/community/modules/user/service/UserService.java)
- [ContentService.java](../backend/src/main/java/com/community/modules/content/service/ContentService.java)

**问题描述**：
同一个项目中存在三种不同的 Service 设计模式：

| Service | 行数 | 设计模式 |
|---------|------|----------|
| ActivityService | 168行 | 纯委托层，所有方法转发给 Query/Command Service |
| UserService | 543行 | 包含所有业务逻辑的"上帝 Service" |
| ContentService | 335行 | 纯委托层，转发给 Query/Command Service |

**影响**：
- 开发者无法预测新功能应该遵循哪种模式
- 代码审查标准不一致
- 新成员学习成本增加

**建议**：
- 统一采用 CQRS 模式或统一采用单一 Service 模式
- 如果采用 CQRS，应该有统一的抽象层或接口约束

---

### 3. BaseEntity 缺失关键字段

**位置**：[BaseEntity.java](../backend/src/main/java/com/community/common/entity/BaseEntity.java)

**问题描述**：
BaseEntity 只有 `createTime` 和 `updateTime` 两个字段，缺失常见的审计字段：

```java
@Data
public class BaseEntity {
    @TableField(fill = FieldFill.INSERT)
    private LocalDateTime createTime;

    @TableField(fill = FieldFill.INSERT_UPDATE)
    private LocalDateTime updateTime;
}
```

**缺失字段**：
- `id` - 每个实体都要自己声明 `@TableId`
- `deleted` - 软删除标记
- `version` - 乐观锁字段
- `createdBy` - 创建人审计
- `updatedBy` - 更新人审计

**影响**：
- BaseEntity 提供的价值有限
- 每个实体都有重复的 id 声明
- 无法实现统一的软删除和乐观锁机制

**建议**：
- 完善 BaseEntity，添加通用字段
- 或明确 BaseEntity 的定位，仅作为时间审计基类

## 二、安全性问题

### 4. JWT Secret 硬编码默认值

**位置**：[application.yml](../backend/src/main/resources/application.yml)

```yaml
app:
  jwt:
    secret: ${APP_JWT_SECRET:CVS_DEV_ONLY_CHANGE_ME_BEFORE_DEPLOYMENT_2026}
    expire-seconds: 86400
```

**问题描述**：
- 默认值长度只有 46 字符，对于 HMAC-SHA256 勉强够用
- 生产环境可能忘记修改默认值
- 没有启动时强制校验机制

**影响**：
- 生产环境可能使用不安全的密钥
- JWT 令牌可能被伪造

**建议**：
- 添加启动时校验，生产环境必须配置自定义密钥
- 密钥长度至少 256 位（32 字节）
- 考虑使用密钥管理服务（如 Vault）

---

### 5. 前端 Token 存储在 localStorage

**位置**：[auth.ts](../Frontend/src/utils/auth.ts)

```typescript
export function setToken(token: string) {
  localStorage.setItem(TOKEN_KEY, token)
}
```

**问题描述**：
- localStorage 容易受到 XSS 攻击
- 任何注入的脚本都能读取 token
- 不符合 OWASP 安全最佳实践

**影响**：
- XSS 攻击可窃取用户令牌
- 跨站脚本攻击风险增加

**建议**：
- 使用 HttpOnly Cookie 存储 token
- 配合 SameSite 属性防止 CSRF
- 或使用 sessionStorage（至少关闭标签页后失效）

---

### 6. 密码验证错误信息可能泄露信息

**位置**：[AuthService.java](../backend/src/main/java/com/community/modules/auth/service/AuthService.java)

```java
private static final String LOGIN_FAILED_MESSAGE = "账号、密码或登录入口错误";
```

**问题描述**：
- 虽然错误信息模糊，但攻击者可通过时序攻击区分"用户不存在"和"密码错误"
- 数据库查询用户存在与否的时间不同

**影响**：
- 攻击者可枚举有效用户名
- 为暴力破解提供信息

**建议**：
- 使用恒定时间比较算法
- 无论用户是否存在，都执行密码哈希比较

---

### 7. SecurityConfig 中的公开接口暴露过多

**位置**：[SecurityConfig.java](../backend/src/main/java/com/community/common/config/SecurityConfig.java)

**问题描述**：
大量 GET 接口公开访问，但没有统一的速率限制：
- `/api/content/mall-products/page` - 积分商城公开访问
- `/api/activity/page` - 活动列表公开访问
- `/api/content/forum/posts/page` - 论坛帖子公开访问

**影响**：
- 可能被爬虫滥用
- 服务器资源被恶意消耗
- 敏感数据可能被批量抓取

**建议**：
- 添加 API 速率限制（如 Bucket4j 或 Redis 限流）
- 敏感接口要求登录访问
- 添加请求频率监控

## 三、数据一致性问题

### 8. 积分扣减存在并发竞争条件

**位置**：[ContentCommandService.java](../backend/src/main/java/com/community/modules/content/service/ContentCommandService.java)

```java
int userUpdated = userMapper.update(null, new UpdateWrapper<User>()
        .eq("id", userId)
        .ge("points", totalPoints)
        .setSql("points = coalesce(points, 0) - " + totalPoints));
if (userUpdated != 1) {
    throw new BusinessException(ApiErrorCode.BUSINESS_CONFLICT, "Current points are not enough for this exchange");
}
```

**问题描述**：
- 高并发下用户可能同时发起多个兑换请求
- 没有使用数据库行锁或分布式锁
- 订单创建和积分扣减的原子性依赖事务，但异常处理可能不完整

**影响**：
- 用户可能用相同积分兑换多件商品
- 数据不一致风险

**建议**：
- 使用 `SELECT ... FOR UPDATE` 行锁
- 或使用 Redis 分布式锁
- 或使用乐观锁（version 字段）

---

### 9. 订单号生成器的线程安全和分布式问题

**位置**：[ContentCommandService.java](../backend/src/main/java/com/community/modules/content/service/ContentCommandService.java)

```java
private final AtomicInteger orderSequence = new AtomicInteger();
private LocalDate orderSequenceDate = LocalDate.now();

private synchronized String nextOrderNo() {
    LocalDate today = LocalDate.now();
    if (!today.equals(orderSequenceDate)) {
        orderSequenceDate = today;
        orderSequence.set(0);
    }
    int sequence = orderSequence.updateAndGet(current -> current >= 999 ? 1 : current + 1);
    return "ORD" + LocalDateTime.now().format(SERIAL_TIME_FORMAT) + String.format("%03d", sequence);
}
```

**问题描述**：
- `orderSequenceDate` 不是线程安全的（虽然方法有 synchronized）
- `synchronized` 在单机有效，多实例部署时序列号会重复
- 性能瓶颈：所有订单创建都要竞争同一把锁

**影响**：
- 多实例部署时订单号可能重复
- 高并发时性能下降

**建议**：
- 使用数据库序列
- 使用 Snowflake 等分布式 ID 生成器
- 或使用 Redis 原子递增

### 10. 删除志愿者时的级联删除问题

**位置**：[UserService.java](../backend/src/main/java/com/community/modules/user/service/UserService.java)

```java
public void deleteVolunteer(Long id) {
    // ...
    activityApplicationMapper.delete(...);
    activityCheckRecordMapper.delete(...);
    forumPostMapper.delete(...);
    commentInfoMapper.delete(...);
    favoriteActivityMapper.delete(...);
    volunteerCertificationMapper.delete(...);
    pointsChangeLogMapper.delete(...);
    userMapper.deleteById(id);
}
```

**问题描述**：
- 7 个删除操作 + 1 个用户删除，共 8 个数据库操作
- 如果中间某一步失败，之前的数据已被删除
- 没有使用数据库外键级联删除
- 删除用户数据是否符合数据保留合规要求？

**影响**：
- 数据不一致风险
- 可能违反数据保留法规
- 审计追踪中断

**建议**：
- 使用软删除代替物理删除
- 或使用数据库外键级联
- 保留用户操作日志用于审计

## 四、代码质量问题

### 11. 大量重复的参数校验代码

**位置**：
- [ActivityCommandService.java](../backend/src/main/java/com/community/modules/activity/service/ActivityCommandService.java)
- [ContentCommandService.java](../backend/src/main/java/com/community/modules/content/service/ContentCommandService.java)
- [UserService.java](../backend/src/main/java/com/community/modules/user/service/UserService.java)

**问题描述**：
每个 Service 都有类似的校验方法：

```java
private String requireText(String value, String message) { ... }
private String normalizeOptionalText(String value) { ... }
private int normalizeBinaryValue(...) { ... }
```

**影响**：
- 代码重复
- 校验逻辑不一致风险
- 修改时需要多处同步

**建议**：
- 提取到公共工具类 `ValidationUtils`
- 或使用 Bean Validation 注解
- 或创建统一的参数校验切面

---

### 12. 魔法字符串泛滥

**问题描述**：
整个代码库中充斥着魔法字符串：

| 类型 | 示例值 |
|------|--------|
| 状态 | `"PENDING"`, `"APPROVED"`, `"REJECTED"`, `"ARCHIVED"`, `"PUBLISHED"`, `"ENDED"` |
| 角色 | `"ADMIN"`, `"VOLUNTEER"` |
| 目标类型 | `"ACTIVITY"`, `"POST"` |

**影响**：
- 拼写错误无法在编译时发现
- 重构困难
- IDE 无法提供自动补全

**建议**：
- 创建枚举类：`ActivityStatus`, `ApplicationStatus`, `UserRole`, `CommentTargetType`
- 数据库使用 `@Enumerated` 或自定义 TypeHandler

---

### 13. 异常处理不够精细

**位置**：[BusinessException.java](../backend/src/main/java/com/community/common/exception/BusinessException.java)

```java
public BusinessException(Integer code, String message) {
    this(ApiErrorCode.fromCode(code), message);

```

**问题描述**：
- 允许任意 code 值，可能导致错误码不一致
- 没有错误码注册机制
- 异常信息直接暴露给前端

**影响**：
- 错误码冲突风险
- 敏感信息泄露
- 国际化困难

**建议**：
- 创建错误码注册表
- 区分内部错误信息和用户友好信息
- 支持国际化错误消息

### 14. DashboardService 直接拼接 SQL

**位置**：[DashboardService.java](../backend/src/main/java/com/community/modules/dashboard/service/DashboardService.java)

result.put("activityCount", queryCount("select count(1) from activity where status <> 'ARCHIVED' or status is null"));

- 重构困难
- 代码可读性差

**建议**：

- 或使用 QueryWrapper 构造查询

## 六、数据库设计问题

### 18. V1 迁移脚本包含大量条件判断

**位置**：[V1__baseline_schema.sql](../backend/src/main/resources/db/migration/V1__baseline_schema.sql)

```sql
SET @activity_cover_exists = (SELECT COUNT(*) FROM information_schema.COLUMNS ...);
SET @activity_cover_sql = IF(@activity_cover_exists = 0, 'ALTER TABLE ...', 'SELECT 1');
PREPARE activity_cover_stmt FROM @activity_cover_sql;
EXECUTE activity_cover_stmt;
```

**问题描述**：
- Flyway 迁移脚本依赖运行时条件判断
- 说明迁移脚本是在已有数据库上逆向生成的
- 违反了 Flyway 的设计理念

**影响**：
- 迁移脚本可预测性差
- 新环境初始化可能出现问题
- 调试困难

**建议**：
- 重新设计迁移脚本，确保幂等性
- 使用 Flyway 的 baseline 机制处理历史数据

---

### 19. 缺少数据库索引策略

**问题描述**：
观察表结构，多个关键字段缺少索引：

**影响**：

**建议**：
- 分析实际查询模式

## 九、业务逻辑问题

### 26. 报名撤销窗口只有 30 秒

**位置**：[ActivityCommandService.java](../backend/src/main/java/com/community/modules/activity/service/ActivityCommandService.java)

```java
private static final Duration APPLICATION_UNDO_WINDOW = Duration.ofSeconds(30);
```

**问题描述**：
- 30 秒对于用户来说太短
- 审核前应该都可以撤销

**影响**：
- 用户误操作无法补救
- 增加管理员审核工作量

**建议**：
- 延长撤销窗口至审核前
- 或配置化撤销时间

### 27. 积分系统缺少防作弊机制

**问题描述**：
观察积分相关代码，缺少防作弊机制：
- 没有单日积分获取上限
- 没有异常行为检测
- 没有积分过期机制

**影响**：
- 志愿者可能刷积分
- 积分通胀风险

**建议**：
- 添加单日积分上限
- 异常行为告警
- 积分有效期机制

### 核心问题

项目缺乏统一的技术规范和架构约束，导致不同模块采用了不同的设计模式，增加了维护成本和理解难度。

### 建议优先级

1. **P0 - 立即修复**：安全性问题（JWT Secret、Token 存储）、数据一致性问题（积分并发）
2. **P1 - 短期修复**：架构设计统一、测试覆盖提升
3. **P2 - 中期优化**：代码质量、数据库索引、日志规范
4. **P3 - 长期改进**：文档完善、技术债务清理
