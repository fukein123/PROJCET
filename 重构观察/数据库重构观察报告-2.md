# 数据库深度重构观察报告

> 观察日期：2026-03-15
> 项目：社区志愿服务管理平台 (zero2.0)
> 数据库：MySQL 8 + Flyway 迁移

---

## 一、迁移脚本问题

### 1. 迁移脚本严重违反 Flyway 设计理念

**位置**：`backend/src/main/resources/db/migration/`

**问题描述**：
所有迁移脚本（V1、V2、B1）都包含大量运行时条件判断：

```sql
SET @activity_cover_exists = (
    SELECT COUNT(*)
    FROM information_schema.COLUMNS
    WHERE TABLE_SCHEMA = DATABASE()
      AND TABLE_NAME = 'activity'
      AND COLUMN_NAME = 'cover_image'
);
SET @activity_cover_sql = IF(@activity_cover_exists = 0,
                             'ALTER TABLE activity ADD COLUMN cover_image VARCHAR(255) NULL AFTER description',
                             'SELECT 1');
PREPARE activity_cover_stmt FROM @activity_cover_sql;
EXECUTE activity_cover_stmt;
```

**问题分析**：
- Flyway 的核心设计理念是：每个迁移脚本应该是确定性的、只执行一次
- 这种模式说明迁移脚本是在已有数据库上"打补丁"逆向生成的
- 违反了 Flyway 的版本控制原则

**影响**：
- 迁移脚本可预测性差
- 新环境初始化可能出现问题
- 团队成员无法确定数据库的真实状态
- 迁移失败时难以定位问题

**建议**：
- 重新设计迁移策略，确保每个版本只做一件事
- 使用 Flyway 的 `baseline-on-migrate` 正确处理历史数据库
- 新增表/字段应该只在一个版本中定义

### 2. V1 与 B1 内容高度重复

**位置**：
- [V1__baseline_schema.sql](../backend/src/main/resources/db/migration/V1__baseline_schema.sql)
- [B1__baseline_schema.sql](../backend/src/main/resources/db/migration/B1__baseline_schema.sql)

**问题描述**：
两个文件内容几乎完全相同，都包含：
- 完整的表结构定义
- 相同的条件判断逻辑

**问题分析**：
- B1 是 Flyway 的 baseline 版本，应该是一个"空"版本或最小版本
- V1 应该是真正的第一个迁移版本
- 两者重复会导致混淆

**建议**：
- B1 应该只包含 Flyway baseline 标记
- V1 应该包含完整的初始表结构（无条件判断）

---

### 3. V1 与 V2 存在重复的 ALTER TABLE 语句

**问题描述**：
以下字段在 V1 和 V2 中都被添加：

| 表 | 字段 | V1 | V2 |
|----|------|----|----|
| activity | cover_image | ✓ | ✓ |
| activity | volunteer_quota | ✓ | ✓ |
| activity | content | ✓ | ✓ |
| info_dynamic | image_url | ✓ | ✓ |
| comment_info | test_data_tag | ✓ | ✓ |
| favorite_activity | note/tag/priority | ✓ | ✓ |

**问题分析**：
- 如果 V1 已经执行过，V2 的条件判断会跳过（这是正确的）
- 但这表明迁移脚本是在已有数据库上逐步"补丁"形成的
- 新环境初始化时，V1 和 V2 都会执行，造成冗余

**建议**：
- 清理重复的迁移逻辑
- 每个字段的添加应该只在一个版本中出现

### 4. V7 包含乱码修复逻辑

**位置**：[V7__iteration1_database_cleanup.sql](../backend/src/main/resources/db/migration/V7__iteration1_database_cleanup.sql)

- 确保数据库连接使用正确的字符集（utf8mb4）
- 在应用层添加字符编码过滤器

## 二、表结构设计问题

### 5. 完全缺失外键约束

**问题描述**：
整个数据库没有任何外键约束（FOREIGN KEY）。

**影响分析**：

| 关系 | 缺失约束 | 风险 |
|------|----------|------|
| activity.category_id → activity_category.id | 无约束 | 删除分类后活动变成孤儿记录 |
| activity.creator_id → sys_user.id | 无约束 | 删除用户后活动创建者丢失 |
| activity_application.activity_id → activity.id | 无约束 | 删除活动后报名记录残留 |
| activity_application.user_id → sys_user.id | 无约束 | 删除用户后报名记录残留 |
| forum_post.category_id → forum_category.id | 无约束 | 删除分类后帖子变成孤儿 |
| forum_post.user_id → sys_user.id | 无约束 | 删除用户后帖子作者丢失 |
| comment_info.user_id → sys_user.id | 无约束 | 删除用户后评论残留 |
| banner_info.activity_id → activity.id | 无约束 | 删除活动后轮播图关联失效 |
| exchange_order.user_id → sys_user.id | 无约束 | 删除用户后订单残留 |
| exchange_order.product_id → mall_product.id | 无约束 | 删除商品后订单关联失效 |
| volunteer_certification.user_id → sys_user.id | 无约束 | 删除用户后认证记录残留 |

**建议**：
- 添加外键约束，确保引用完整性
- 或在应用层实现级联删除逻辑（当前代码部分实现）

---

### 6. 状态字段使用 VARCHAR 而非 ENUM

**问题描述**：
所有状态字段使用 `VARCHAR(32)` 存储：

| 表 | 状态字段 | 可能值 |
|----|----------|--------|
| activity | status | PUBLISHED, ENDED, ARCHIVED |
| activity_application | status | PENDING, APPROVED, REJECTED |
| activity_check_record | status | SIGNED_IN, FINISHED |
| forum_post | status | PENDING, APPROVED, REJECTED, ARCHIVED |
| exchange_order | status | CREATED, SHIPPED, RECEIVED, CANCELLED |
| volunteer_certification | status | PENDING, APPROVED, REJECTED, NOT_SUBMITTED |

**问题分析**：
- VARCHAR 允许任意值，没有数据校验
- 占用更多存储空间
- 查询效率低于 ENUM

**建议**：
- 使用 MySQL ENUM 类型：`ENUM('PENDING', 'APPROVED', 'REJECTED')`
- 或使用 TINYINT + 应用层枚举映射
- 添加 CHECK 约束（MySQL 8 支持）

### 7. 冗余数据存储问题

#### 7.1 favorite_activity 存储活动快照

**位置**：[V1__baseline_schema.sql](../backend/src/main/resources/db/migration/V1__baseline_schema.sql)

```sql
CREATE TABLE IF NOT EXISTS favorite_activity (
    ...
    activity_id BIGINT NOT NULL,
    activity_title VARCHAR(255),      -- 冗余
    activity_address VARCHAR(255),    -- 冗余
    activity_start_time DATETIME,     -- 冗余
    activity_end_time DATETIME,       -- 冗余
    ...
);
```

**问题分析**：
- 活动信息变更后，收藏记录不会同步更新
- 数据不一致风险
- 存储空间浪费

**建议**：
- 方案一：仅存储 `activity_id`，查询时 JOIN
- 方案二：明确这是"收藏时刻快照"的设计意图，添加注释说明

#### 7.2 exchange_order 存储大量冗余信息

**位置**：[ExchangeOrder.java](../backend/src/main/java/com/community/modules/content/entity/ExchangeOrder.java)

```java
private Long userId;
private Long productId;
private String userName;          // 冗余：可从 sys_user 获取
private String realName;          // 冗余：可从 sys_user 获取
private String productName;       // 冗余：可从 mall_product 获取
private String productImage;      // 冗余：可从 mall_product 获取
private String productSummary;    // 冗余：可从 mall_product 获取
private Integer pointsPerItem;    // 冗余：可从 mall_product 获取
```

**问题分析**：
- 商品信息变更后，历史订单显示的是旧信息（这是合理的设计）
- 但用户名、真实姓名也会变更，订单记录不会更新

**建议**：
- 商品快照保留（合理设计）
- 用户信息考虑是否需要快照

### 8. 字段命名不一致

**问题描述**：

| 问题 | 表 A | 表 B | 说明 |
|------|------|------|------|
| 时间字段命名 | `apply_time` | `submit_time` | 申请时间 vs 提交时间 |
| 审核人命名 | `auditor_id` | `operator_id` | 审核人 vs 操作人 |
| 状态字段类型 | `status TINYINT` | `status VARCHAR(32)` | 部分表用数字，部分用字符串 |

**影响**：
- 代码可读性差
- 开发者需要记忆不同表的命名

**建议**：
- 统一命名规范
- 创建数据库设计规范文档

---

### 9. 缺少必要的审计字段

**问题描述**：
部分表缺少审计字段：

| 表 | 缺失字段 |
|----|----------|
| activity | `created_by`, `updated_by` |
| forum_post | `updated_by` |
| comment_info | `updated_by` |
| mall_product | `created_by`, `updated_by` |

**影响**：
- 无法追踪记录的创建者和最后修改者
- 审计追踪不完整

**建议**：
- 统一添加审计字段
- 或在 BaseEntity 中定义

## 三、索引设计问题

### 10. 缺少关键索引

**问题描述**：
以下高频查询字段缺少索引：

| 表 | 缺失索引字段 | 查询场景 |
|----|-------------|----------|
| activity | `creator_id` | 按创建者查询活动 |
| activity | `status` | 按状态筛选活动 |
| activity_application | `user_id` | 查询用户报名记录 |
| activity_application | `create_time` | 按时间排序 |
| activity_check_record | `user_id` | 查询用户打卡记录 |
| activity_check_record | `status` | 按状态筛选 |
| forum_post | `user_id` | 查询用户帖子 |
| forum_post | `create_time` | 按时间排序 |
| comment_info | `user_id` | 查询用户评论 |
| comment_info | `create_time` | 按时间排序 |
| exchange_order | `status` | 按状态筛选订单 |
| exchange_order | `create_time` | 按时间排序 |
| volunteer_certification | `user_id` | 已有唯一约束，但可优化 |
| volunteer_weekly_stats | `user_id` | 查询用户周统计 |

**建议添加的索引**：

```sql
-- activity
CREATE INDEX idx_activity_creator ON activity (creator_id);
CREATE INDEX idx_activity_status ON activity (status, create_time);

-- activity_application
CREATE INDEX idx_activity_application_user ON activity_application (user_id, create_time);

-- activity_check_record
CREATE INDEX idx_activity_check_record_user ON activity_check_record (user_id);

-- forum_post
CREATE INDEX idx_forum_post_user ON forum_post (user_id, create_time);

-- comment_info
CREATE INDEX idx_comment_info_user ON comment_info (user_id, create_time);

-- exchange_order
CREATE INDEX idx_exchange_order_status_time ON exchange_order (status, create_time);
```

---

### 11. 索引设计不合理

**问题描述**：

| 表 | 现有索引 | 问题 |
|----|----------|------|
| activity | `idx_activity_time (start_time, end_time)` | 范围查询索引效率低 |
| forum_post | `idx_post_status (status)` | 单列索引，应包含 create_time |
| activity_application | `idx_application_status (status)` | 单列索引，应包含 create_time |

**建议**：
- 复合索引应遵循最左前缀原则
- 状态字段索引应包含时间字段用于排序

---

### 12. 缺少覆盖索引

**问题描述**：
高频查询场景缺少覆盖索引，导致回表查询。

**示例**：
```sql
-- 查询用户的活动收藏列表
SELECT activity_id, activity_title, activity_start_time 
FROM favorite_activity 
WHERE user_id = ? 
ORDER BY create_time DESC;
```

**建议**：
```sql
CREATE INDEX idx_favorite_user_time ON favorite_activity (user_id, create_time DESC, activity_id);
```

## 四、数据类型问题

### 13. 字段长度设计不合理

**问题描述**：

| 表 | 字段 | 当前类型 | 问题 |
|----|------|----------|------|
| sys_user | password | VARCHAR(128) | BCrypt 固定 60 字符，128 过长 |
| sys_user | phone | VARCHAR(32) | 手机号固定 11 位，32 过长 |
| activity | content | VARCHAR(500) | 活动简介可能超过 500 字符 |
| comment_info | content | VARCHAR(500) | 评论可能超过 500 字符 |
| forum_post | title | VARCHAR(255) | 标题通常不超过 100 字符 |

**建议**：
- 根据实际业务需求调整字段长度
- 过长的字段浪费存储和内存

---

### 14. 数值字段缺少范围约束

**问题描述**：

| 表 | 字段 | 当前定义 | 问题 |
|----|------|----------|------|
| activity | target_count | INT | 无最小值约束，可为负数 |
| activity | volunteer_quota | INT | 无最小值约束 |
| activity | point_reward | INT | 无最小值约束 |
| mall_product | points_cost | INT | 无最小值约束 |
| mall_product | stock | INT | 无最小值约束 |
| sys_user | points | INT | 无最小值约束 |

**建议**：
```sql
ALTER TABLE activity ADD CONSTRAINT chk_activity_target_count CHECK (target_count > 0);
ALTER TABLE activity ADD CONSTRAINT chk_activity_point_reward CHECK (point_reward >= 0);
ALTER TABLE mall_product ADD CONSTRAINT chk_mall_product_stock CHECK (stock >= 0);
ALTER TABLE sys_user ADD CONSTRAINT chk_sys_user_points CHECK (points >= 0);
```

## 五、种子数据问题

### 16. 密码硬编码在种子数据中

**位置**：[R__seed_reference_data.sql](../backend/src/main/resources/db/migration/R__seed_reference_data.sql)

```sql
INSERT INTO sys_user (id, username, password, ...)
VALUES (1, 'admin', '$2b$10$MdUnSo.DjQ85.dpOSxWW2eTv8RoIJNzNv1P7fcozYwpDsx3Bx6FQK', ...);
```

**问题描述**：
- 密码哈希值硬编码在迁移脚本中
- 如果需要修改默认密码，需要创建新的迁移脚本
- 密码哈希算法变更时需要更新所有迁移脚本

**建议**：
- 使用应用层初始化数据
- 或使用环境变量注入默认密码

---

### 17. 使用外部图片 URL

**问题描述**：
种子数据使用 Unsplash 外部图片：

```sql
'https://images.unsplash.com/photo-1497436072909-60f360e1d4b1?auto=format&fit=crop&w=900&q=80'
```

**影响**：
- 依赖外部服务可用性
- 图片可能被删除或更换
- 网络延迟影响加载速度

**建议**：
- 使用本地静态资源
- 或使用可靠的 CDN 服务

---

### 18. 种子数据 ID 硬编码

**问题描述**：
所有种子数据使用固定 ID：

```sql
INSERT INTO sys_user (id, username, ...) VALUES (1, 'admin', ...);
INSERT INTO sys_user (id, username, ...) VALUES (2, 'volunteer', ...);
INSERT INTO activity_category (id, name, ...) VALUES (1, '社区关爱', ...);
```

**影响**：
- 与 AUTO_INCREMENT 可能冲突
- 如果 ID 已存在，使用 ON DUPLICATE KEY UPDATE 覆盖

**建议**：
- 使用 AUTO_INCREMENT 自动生成 ID
- 或使用 UUID 避免冲突

## 六、表设计缺陷

### 19. volunteer_weekly_stats 设计问题

**位置**：[V1__baseline_schema.sql](../backend/src/main/resources/db/migration/V1__baseline_schema.sql)

```sql
CREATE TABLE IF NOT EXISTS volunteer_weekly_stats (
    ...
    username VARCHAR(64) NOT NULL,   -- 冗余
    real_name VARCHAR(64),           -- 冗余
    ...
);
```

**问题描述**：
- `username` 和 `real_name` 可从 `sys_user` 获取
- 用户信息变更后，统计数据不会更新
- 没有数据生成触发机制

**建议**：
- 仅存储 `user_id`，查询时 JOIN
- 或明确这是"统计时刻快照"的设计意图

---

### 20. 缺少软删除机制

**问题描述**：
所有表都没有 `deleted` 字段，删除操作是物理删除。

**影响**：
- 数据无法恢复
- 审计追踪中断
- 可能违反数据保留法规

**建议**：
- 添加 `deleted` TINYINT 字段
- 或添加 `deleted_at` DATETIME 字段
- 修改应用层查询逻辑

---

### 21. 缺少乐观锁机制

**问题描述**：
所有表都没有 `version` 字段。

**影响**：
- 并发更新时可能丢失更新
- 积分扣减等敏感操作无法防止并发问题

**建议**：
- 添加 `version` INT DEFAULT 0 字段
- 使用 MyBatis-Plus 的 `@Version` 注解

---

## 八、安全问题

### 24. 敏感数据未加密

**问题描述**：

| 表 | 字段 | 风险 |
|----|------|------|
| volunteer_certification | id_card_no | 身份证号明文存储 |
| sys_user | phone | 手机号明文存储 |
| sys_user | email | 邮箱明文存储 |
| exchange_order | receiver_phone | 收货人手机号明文存储 |
| exchange_order | receiver_address | 收货地址明文存储 |

**建议**：
- 敏感字段加密存储
- 使用 AES 或国密算法
- 密钥管理使用 KMS

---

### 25. 缺少数据脱敏机制

**问题描述**：
虽然应用层实现了脱敏（见 UserService），但数据库层面没有保护。

**风险**：
- 数据库备份泄露敏感信息
- DBA 可以直接查看敏感数据

**建议**：
- 数据库层面实现字段级加密
- 或使用 MySQL 的透明数据加密（TDE）

### 核心问题

1. **迁移脚本设计混乱**：大量条件判断违反 Flyway 设计理念
2. **缺失外键约束**：数据完整性依赖应用层，风险高
3. **索引设计不足**：高频查询字段缺少索引，性能隐患
4. **敏感数据未加密**：身份证号等敏感信息明文存储

### 建议优先级

#### P0 - 立即修复
- [ ] 添加敏感字段加密（身份证号、手机号）
- [ ] 添加关键索引（user_id、create_time）
- [ ] 添加数值字段 CHECK 约束

#### P1 - 短期修复
- [ ] 重构迁移脚本，移除条件判断
- [ ] 添加外键约束
- [ ] 统一状态字段类型

#### P2 - 中期优化
- [ ] 添加软删除机制
- [ ] 添加乐观锁机制
- [ ] 优化冗余字段

#### P3 - 长期改进
- [ ] 评估分区策略
- [ ] 评估读写分离
- [ ] 完善审计字段
